1. Flow Control / BS / STmin

FC：30 / 31 / 32

值含义人话
30 / CTSContinue To Send继续发。
31 / WAITWait先等等，我还没准备好。
32 / OVFLWOverflow接收不了，本次传输失败。不是正常结束。

BS / STmin / SN

概念一句话例子
BSReceiver 允许 Sender 连续发多少个 CF。BS=8：8 个 CF 后重新等 FC；BS=0：剩余 CF 可一直发完，不再因 BS 等新 FC。
STminReceiver 要求 Sender 的相邻 CF 最小间隔。00~7F=0~127 ms；F1~F9=100~900 μs。
SNCF 的 Sequence Number，低 4 bit；必须连续。21→22→...→2F→20→21。
BS/STmin 到底谁决定？
我的 ECU 接收多帧 → BS/STmin 由我的 RxNSdu 配置决定，我通过 FC 告诉对方。
我的 ECU 发送多帧 → BS/STmin 由对方 FC 决定，我照着执行。
CanTpChangeParameterApi=OFF 时按 EB 固定配置理解；开启后可通过标准 API 在运行时修改 Rx 侧 BS/STmin。

6. 六个 N_Timer + P2 / P2*

先背两个：N_Bs = Sender 等 FC；N_Cr = Receiver 等下一 CF。

Timer站在哪边人话记忆
N_AsSenderDATA N-PDU 交给下面去发后，这一帧不能一直不完成。
N_BsSender发完 FF / 一个 Block 后，等对方 FC。
N_CsSender轮到继续发 CF 时，准备下一块数据 / 下一 CF 不能拖太久。
N_ArReceiver要发 FC 时，FC 交给下面后不能一直不完成。
N_BrReceiver收到 FF / 到了回 FC 阶段，准备 Buffer 和 FC 不能一直磨蹭。
N_CrReceiver已经允许你发了，现在等下一 CF，不能无限等。
P2UDS / DCMTester 发完 UDS Request 后，等 ECU 开始给诊断响应的时间概念。
P2*UDS / DCMECU 通过 7F xx 78 表示还在处理后，使用更长的后续响应等待时间。
N_xx = CanTp 多帧传输过程时间；P2/P2* = UDS 请求与诊断响应时间。
STmin = 别发太快；N_Cr = 也别让我等太久。

易混淆速查

  1. 30=继续，31=等待，32=接收不了/失败。
  2. BS=0 不是不许发，而是剩余 CF 不再因 Block Size 等新 FC。
  3. STmin 管别太快；N_Cr 管也别让我等太久。
  4. Receiver 决定 BS/STmin，Sender 遵守。
  5. P2/P2* 属于 UDS 响应时间；N_As~N_Cr 属于 CanTp 传输时间。
