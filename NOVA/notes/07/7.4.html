3. RxNSdu / TxNSdu / N-PDU Linking

RxNSdu
完整接收连接：收 DATA + 发 FC。典型关联：RxNPdu + TxFcNPdu。
TxNSdu
完整发送连接：发 DATA + 收 FC。典型关联：TxNPdu + RxFcNPdu。

当前项目实际映射

完整 N-SDU角色DATA N-PDUFC N-PDU
DIAG_REQRxNSdu收：DIAG_REQ_2001R发：DIAG_RES_2009T
DIAG_RESTxNSdu发：DIAG_RES_D_2009T收：DIAG_REQ_2001R
Tester                                      ECU
DIAG_REQ_2001R  ── Request DATA ───────→  RxNSdu
DIAG_RES_2009T  ←────── FC ─────────────  RxNSdu

DIAG_RES_D_2009T←── Response DATA ──────  TxNSdu
DIAG_REQ_2001R  ─────── FC ────────────→  TxNSdu

几个 ID 千万别混

字段编号的是什么特别注意
CanTpRxNSduId / CanTpTxNSduId完整 Rx/Tx N-SDU 配置的 Handle / 编号。不是 CAN ID。
CanTpRxNPduId / RxFcNPduIdCanTp 收到底层某条 N-PDU 时识别它的 Handle。数字就算与 NSduId 都是 0，也不是同一个概念。
CanTpTxNPduConfirmationPduIdCanIf 回调 CanTp_TxConfirmation(PduId) 时，CanTp 用它识别哪条 Tx N-PDU 发完。同样不是 CAN Identifier。

4. AUTOSAR API 命名 + 调用栈

下划线前第一个模块名 = 这个 API 属于哪个模块。
CanTp_Transmit() 属于 CanTp；PduR_CanTpCopyTxData() 属于 PduR。
但仅凭函数名不能保证知道是谁调用它；调用者要看 AUTOSAR 接口关系 / 实际调用链。

发送方向

顺序调用关系API人话
1PduR 调用 CanTp 的 APICanTp_Transmit()开始发送整个 N-SDU。
2CanTp 调用 PduR 的 APIPduR_CanTpCopyTxData()CanTp：给我下一块发送数据。
3CanTp 调用 CanIf 的 APICanIf_Transmit()把一个 SF / FF / CF / FC N-PDU 交给 CanIf。
4CanIf 调用 CanTp 的 APICanTp_TxConfirmation()刚才一个 N-PDU 发完了。
多帧CanIf 调用 CanTp 的 APICanTp_RxIndication()对方 FC 作为 Rx N-PDU 进入 CanTp。
最后CanTp 调用 PduR 的 APIPduR_CanTpTxConfirmation()整个 N-SDU 全部发送结束。
CanTp_TxConfirmation = 一个 N-PDU 完成；PduR_CanTpTxConfirmation = 整个 N-SDU 完成。

接收方向

顺序调用关系API人话
1CanIf 调用 CanTp 的 APICanTp_RxIndication()一个 SF / FF / CF / FC 进入 CanTp。
2CanTp 调用 PduR 的 APIPduR_CanTpStartOfReception()开始收完整 N-SDU，先确认 / 准备 Rx Buffer。
3CanTp 调用 PduR 的 APIPduR_CanTpCopyRxData()把刚收到的一块有效数据交给上层 Buffer。
需要FCCanTp 调用 CanIf 的 APICanIf_Transmit()Receiver 收到 FF 后发 FC。
最后CanTp 调用 PduR 的 APIPduR_CanTpRxIndication()整个 N-SDU 接收结束。

重要 API：以后查断点时看这张

API它管什么什么现象时最值得看
CanTp_Transmit()开始发送整个 N-SDU。上层已经准备 Response，但 CanTp 根本没开始。
PduR_CanTpCopyTxData()向上层拿下一块 Tx 数据。CanTp 已开始，但后续数据拿不到 / CF 准备不出来。
CanIf_Transmit()把一个 N-PDU 交给 CanIf。CanTp 已决定要发，但总线没看到对应帧。
CanTp_TxConfirmation()一个 Tx N-PDU 发送完成。总线已经发了，但 CanTp 状态不继续。
CanTp_RxIndication()一个 Rx N-PDU 进入 CanTp。CANoe 看见帧，但 CanTp 没收到。
PduR_CanTpStartOfReception()开始接收并确认 Rx Buffer。FF 已进入 CanTp，但完整接收流程没建立。
PduR_CanTpCopyRxData()把每一块 Rx 数据交给上层。CF 在进，但上层数据没有持续累积。
PduR_CanTpRxIndication()通知上层整个 N-SDU 接收结束。全部收齐，但上层不知道完成。

5. Buffer 机制

CanTp 主要做流式搬运：发送时向 PduR 一块一块取；接收时一块一块交给 PduR，不要把它理解成自己先囤完整几 KB 数据。

Rx
收到 FF
→ StartOfReception()
  “我要收这么大的 N-SDU，有没有地方放？”
→ CopyRxData()
  FF/CF 数据一块一块交上去
→ RxIndication()
  整个 N-SDU 收完
Tx
上层要发大 N-SDU
→ CanTp_Transmit()
→ CopyTxData()
  先拿 FF 数据
→ CopyTxData()
  再拿下一个 CF 数据
→ ...
→ TxConfirmation()
  整个 N-SDU 完成
BufReq 返回人话联想
BUFREQ_OK可以，Buffer / 数据准备好了。继续。
BUFREQ_E_BUSY现在暂时没准备好，稍后再试。Tx 时尤其联想到 N_Cs。
BUFREQ_E_OVFL数据太大，接收 Buffer 放不下。Receiver 无法继续正常接收。
BUFREQ_E_NOT_OK这次 Buffer / 数据操作无法完成。当前传输不能正常继续。

7. EB：CanTpRxNSdu 核心配置（当前项目）

配置项当前值人话解释
CanTpBs0本 ECU 作为 Receiver 时告诉 Sender：剩余 CF 可连续发完，不因 BS 再停下来等 FC。
CanTpNar0.025 sN_Ar = 25 ms：Receiver 发 FC 这一帧的发送完成时间约束。
CanTpNbr0.1 sN_Br = 100 ms：Receiver 到了要发 FC 的阶段，准备 Buffer / FC 的时间约束。
CanTpNcr0.15 sN_Cr = 150 ms：Receiver 等下一 CF 的时间约束。
CanTpRxNSduId0完整 Rx N-SDU 的 CanTp Handle / 编号；不是 CAN ID。
CanTpRxPaddingActivationCANTP_ON这条 Rx N-SDU 开启 Padding 处理；Padding 填充值看 General 的 CanTpPaddingByte。
CanTpRxTaTypeCANTP_PHYSICAL这条 RxNSdu 是物理寻址，即针对本 ECU 的 1:1 请求。
CanTpRxWftMax4Receiver 最多允许多少次 FC WAIT(31)；不能无限 WAIT。
CanTpSTmin0.01 sReceiver 要求对方：CF 之间至少 10 ms；与 BS=0 合起来，典型 FC 是 30 00 0A。
CanTpRxNSduRefDIAG_REQ上层眼中的完整诊断 Request N-SDU。
CanTpRxAddressingFormatCANTP_STANDARD地址由 CAN ID 区分；Payload Byte0 直接是 PCI。
CanTpRxNPduRefDIAG_REQ_2001RSF / FF / CF 这些Request DATA 从这里收。
CanTpTxFcNPduRefDIAG_RES_2009T收到多帧 Request 的 FF 后，FC 从这里发。

8. EB：CanTpTxNSdu 核心配置（当前项目）

配置项当前值人话解释
CanTpNas0.025 sN_As = 25 ms：Sender 发一个 DATA N-PDU 时，这一帧的发送完成时间约束。
CanTpNbs0.075 sN_Bs = 75 ms：Sender 发 FF / 一个 Block 后，等待对方 FC。
CanTpNcs0.9 sN_Cs = 900 ms：到了继续发 CF 的阶段，准备下一块数据 / 下一 CF 的时间约束。
CanTpTcON这条 Tx N-SDU 允许 transmission cancellation；实际对外 Cancel API 是否生成还要同时看 General / Vendor 配置。
CanTpTxDl1旧/遗留参数；不要把 1 理解成 CAN 帧只有 1 Byte，也不要靠它判断实际 CAN 帧长度。
CanTpTxNSduId0完整 Tx N-SDU 的 CanTp Handle / 编号；不是 CAN ID。
CanTpTxPaddingActivationCANTP_ON这条 Tx N-SDU 开启 Padding；未使用 Byte 用 General 的 PaddingByte 补齐。
CanTpTxTaTypeCANTP_PHYSICAL这条 TxNSdu 是物理响应；CanTp 标准 Tx 侧使用 Physical 通信。
CanTpTxNSduRefDIAG_RES上层眼中的完整诊断 Response N-SDU；CanTp 再把它拆成 SF / FF / CF。
CanTpTxAddressingFormatCANTP_STANDARD地址由 CAN ID 区分；Payload Byte0 直接是 PCI。
CanTpRxFcNPduRefDIAG_REQ_2001RECU 发多帧 Response 时，Tester 的 FC 从这里收。
CanTpTxNPduRefDIAG_RES_D_2009TResponse 的 SF / FF / CF 从这条 Tx N-PDU 发。
CanTpTxNPduConfirmationPduId0CanIf 回调 CanTp_TxConfirmation() 时，CanTp 用它知道哪条 Tx N-PDU 已完成。

9. EB General：真正值得以后查的配置

配置开启时关闭时对应 API / 影响
CanTpChangeParameterApi
当前 OFF		允许运行时修改 Rx N-SDU 的 BS / STmin。BS/STmin 按 EB 配置使用，不能通过该标准 API 动态修改。CanTp_ChangeParameter(...)
CanTpReadParameterApi
当前 OFF		允许读取当前 Rx N-SDU 的 BS / STmin。不提供该读取能力。CanTp_ReadParameter(...)
CanTpCancelReceiveApi
当前 OFF		上层可主动终止正在进行的整个 N-SDU 接收。不提供该标准 Cancel Receive API。CanTp_CancelReceive(...)
CanTpCancelTransmitApi
当前 OFF		上层可主动终止正在进行的整个 N-SDU 发送。不提供该标准 Cancel Transmit API。CanTp_CancelTransmit(...)
CanTpChangeTxParameterApi
当前 OFF		启用发送侧参数动态修改相关能力（EB/Vendor 扩展项）。不启用该发送侧动态修改能力。精确 API 名称和可修改参数以当前 Vendor 的 CanTp.h / EB Help 为准；不要凭字段名猜 API。
CanTpPaddingByte开启 Tx Padding 时，未使用的 CAN Payload Byte 用该值补齐。当前项目：0x00。
CanTpFlexibleDataRateSupportCanTp 支持 CAN FD。不使用该 CAN FD 支持能力。当前项目：ON。
CanTpDynIdSupport / GenericConnectionSupport支持 MetaData / 动态寻址或通用连接类高级场景。普通固定诊断连接按静态关联工作。当前项目 OFF；固定 DIAG_REQ / DIAG_RES 一般不用。
Cancel ≠ Timeout：Cancel 是上层主动终止；N_Bs / N_Cr 等 timeout 是协议传输过程超时导致失败。

DevErrorDetect、VersionInfo、MultiCore、Relocatable PB、MaxChannel、GPT、Stall、Dedicated Processing 等实现/资源类开关不放进核心区；普通 CanTp 报文与诊断学习中优先级低。

10. CanTpConfig / Channel

CanTpConfig
一整套 CanTp 配置集合。不要把“两个 CanTpConfig”机械理解成一个 Physical、一个 Functional。判断 Physical/Functional 看 TaType。
CanTpChannel
CanTp 跑 TP 会话用的状态机 / 运行资源：记录状态、SN、剩余长度、BS Counter、Timer、当前 N-SDU 等。
NSdu = 配置好的通信连接；Channel = 真正运行连接时用的状态机工作台。一个 Channel 可以关联多个 N-SDU，从而复用内部资源。
Channel Mode人话
FULL_DUPLEX同一 Channel 的 Tx / Rx 方向可按全双工方式并行处理。
HALF_DUPLEX同一 Channel 的 Tx / Rx 不按全双工方式同时独立运行，会受到互斥/资源限制。

12. EB 配置一条 CanTp 连接：最短检查顺序

顺序确认什么核心问题
1诊断通信定义Request / Response CAN ID、11/29 bit、Classic/FD、Physical/Functional、Addressing、Padding。
2CanIf Rx/Tx PDURequest Rx PDU、Response Tx PDU 是否已经存在且方向正确。
3CanTp RxNSduDATA 从哪个 RxNPdu 收？FC 从哪个 TxFcNPdu 发？再配 BS、STmin、WFTmax、N_Ar/N_Br/N_Cr、TaType、Addressing。
4CanTp TxNSduDATA 从哪个 TxNPdu 发？FC 从哪个 RxFcNPdu 收？再配 N_As/N_Bs/N_Cs、TaType、Addressing、Padding。
5PduR接收：CanTp → PduR → DCM；发送：DCM → PduR → CanTp 的 N-SDU 路由是否对应。
6整链对应完整 N-SDU、底层 N-PDU、CanIf PDU、CAN ID 的方向是否全部一致。

13. CANoe 看诊断报文：最短读法

看到什么立刻想到什么
03 22 F1 90 ...SF；UDS 长度 3；真正 UDS 是 22 F1 90。
10 24 ...FF；完整 N-SDU 长度 0x024 = 36 Byte。
30 08 0ACTS；最多连续 8 个 CF；CF 最小间隔 10 ms。
21 22 23 ... 2F 20 21CF 的 SN 连续递增，F 后回 0。
Functional Request只能 SF；若 ECU 回很多数据，Response 用 Physical 多帧。
CAN FD 00 LL ...可能是扩展 SF_DL；不要机械套 Classic CAN 的低 4 bit 长度规则。

14. 最容易混淆的 12 句话

  1. N-SDU 是整个数据；N-PDU 是一帧一帧的数据。
  2. FF 中长度是整个 N-SDU 总长度，不是 FF 本帧长度。
  3. 30=继续，31=等待，32=接收不了/失败。
  4. BS=0 不是不许发，而是剩余 CF 不再因 Block Size 等新 FC。
  5. STmin 管别太快；N_Cr 管也别让我等太久。
  6. Receiver 决定 BS/STmin，Sender 遵守。
  7. RxNSdu = 收 DATA + 发 FC；TxNSdu = 发 DATA + 收 FC。
  8. TaType 决定 Physical/Functional；AddressingFormat 决定地址放在哪里。
  9. Functional Request 只用 SF；需要多帧的 Response 走 Physical Tx。
  10. NSduId / NPduId / ConfirmationPduId 都不是 CAN ID。
  11. CanTp_TxConfirmation 是一个 N-PDU 完成；PduR_CanTpTxConfirmation 是整个 N-SDU 完成。
  12. P2/P2* 属于 UDS 响应时间；N_As~N_Cr 属于 CanTp 传输时间。
