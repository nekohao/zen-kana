7. CanNm 配置项

CanNm 负责什么
1. NM 状态机时间：Repeat / Normal / ReadySleep / PrepareBusSleep / BusSleep。
2. NM 报文行为：周期、首发 offset、TxConfirmation timeout。
3. NM PDU 内容：NID、CBV、UserData、PN 信息、CarWakeUp 位。
什么时候重点看 CanNm
周期不对：CanNmMsgCycleTime、Immediate NM、BusLoadReduction。
释放后不睡：CanNmTimeoutTime、CanNmWaitBusSleepTime，先确认本地请求已释放。
内容不对：NodeId、NID/CBV Position、UserDataLength、PN offset。
发送确认异常：CanNmMsgTimeoutTime、CanIf TxConfirmation。
CanNm 排查边界：先确认 ComM 已允许 FullCom、CanSM Controller 已 STARTED、Nm 已触发 NetworkRequest、CanIf TxPduRef/HTH 正确；这些不成立时，改 CanNmMsgCycleTime、RepeatMessageTime、TimeoutTime 通常没用。

7.3 CanNm 状态机粗链路

请求网络时：
ComM FullCom
    -> Nm_NetworkRequest
        -> CanNm_NetworkRequest
            -> Repeat Message
                -> Normal Operation
                    -> 周期发送 NM
释放网络时：
ComM 释放 FullCom
    -> Nm_NetworkRelease
        -> CanNm_NetworkRelease
            -> Ready Sleep
                -> Prepare Bus Sleep
                    -> Bus Sleep
几个时间参数大概落点：
Repeat Message: 看 RMSTime / CanNmRepeatMessageTime(EB)。
Normal Operation 周期发 NM: 看 MsgCycleTime / CanNmMsgCycleTime(EB)。
本节点等待 Tx confirmation: 看 MsgTimeoutTime / CanNmMsgTimeoutTime(EB)。
网络管理超时: 看 CanNmTime / CanNmTimeoutTime(EB)。
Prepare Bus Sleep 等待: 看 WBSTime / CanNmWaitBusSleepTime(EB)。

7.3.1 DF_XY 应用层 NM 状态机（CanM_Nm.c）

项目结论应用层只操控 NETWORK_REQUESTED / NETWORK_RELEASED 两个本地意图；CanNm HSM 才是真正协议状态机。
图上区域读图重点现场判断
A 上半IGN ON 或 IGN_HW 唤醒后，应用层进入 NETWORK_REQUESTED，ComM 请求 FULL，CanNm 请求标志置 1。这是本节点主动保持网络。
A 下半IGN OFF 后不是马上释放；AwakeCntEnd 没到 0 时仍保持 REQUESTED。关 IGN 后继续发一段 NM，优先查 20s 保持计时。
B 上半CanNm 从 BusSleep/Prepare 被 Req/Rx/NetworkStart 拉到 NetworkMode，再经 RepeatMsg 到 NormalOp。Repeat 时间看 CanNmRepeatMessageTime，Normal 周期看 CanNmMsgCycleTime。
B 下半本地释放只清 ReqFlag；协议还要按 ReadySleep、PrepareBusSleep、BusSleep 定时器逐步睡眠。不要把应用 RELEASED 误判成 CanNm 已 BusSleep。
CUserData、状态镜像、CanIf 诊断挡帧是项目层可见表现。诊断帧被挡时看 CanM_Nm_u8NmCurrentState，不要只看 ComM。
读法：先从 A 判断“本节点有没有主动请求”；再从 B 判断“CanNm 协议真实睡到哪一步”；最后用 C 的 UserData / 状态镜像 / CanIf 表现去对 Trace 和调试变量。

7.4 时间参数

MsgCycleTime / CanNmMsgCycleTime(EB)
含义: 正常 NM 报文周期。
当前: 100 ms。
影响:变小，负载增加，网络保持更积极。
变大，负载降低，但可能影响对端 Timeout 判断。
在哪里配:
    CanNm -> CanNm_ChanConfig / CanNmChannelConfig_0(EB) -> MsgCycleTime / CanNmMsgCycleTime(EB)
何时生效: CanNm 已经处于需要周期发送 NM 的状态时生效Controller 没 STARTED、ComM 没 FullCom 时，改这个也不会让 NM 发出来。
CanNmMsgCycleOffset / CanNmMsgCycleOffset(EB)
含义: 本节点 NM 发送相位/首发偏移。
当前: 5 ms。
影响:避免所有节点同时发送 NM。 必须小于 MsgCycleTime。
在哪里配:
    CanNm -> CanNm_ChanConfig / CanNmChannelConfig_0(EB) -> CanNmMsgCycleOffset / CanNmMsgCycleOffset(EB)
何时生效:影响本节点 NM 首发相位。多节点同一网络时用于错开发送时间。
ImmediateNmTransmissions / CanNmImmediateNmTransmissions(EB)；ImmediateNmCycleTime / CanNmImmediateNmCycleTime(EB)
含义: 唤醒或请求网络初期快速发送若干帧 NM。
    ImmediateNmTransmissions / CanNmImmediateNmTransmissions(EB) 决定快发几帧。
    ImmediateNmCycleTime / CanNmImmediateNmCycleTime(EB) 决定这些快发帧之间的间隔。
影响: 打开后可加快唤醒扩散。 但会增加短时间总线负载。
在哪里配: CanNm -> CanNm_ChanConfig / CanNmChannelConfig_0(EB) -> ImmediateNmTransmissions / CanNmImmediateNmTransmissions(EB) / ImmediateNmCycleTime / CanNmImmediateNmCycleTime(EB)
何时生效: 网络请求初期、唤醒初期快速发 NM。
注意: ImmediateNmTransmissions = 0 时，不发 immediate NM。  = 1 时，只快发 1 帧，快发周期没有间隔意义。
    EB 里 ImmediateNmCycleTime / CanNmImmediateNmCycleTime(EB) 的 ENABLE 条件是 
ImmediateNmTransmissions / CanNmImmediateNmTransmissions(EB) > 1。
RMSTime / CanNmRepeatMessageTime(EB)
含义: Repeat 状态持续时间。它是“状态持续窗口”，不是慢发周期。
当前: 515 ms。
影响: 影响唤醒扩散、节点发现、Repeat Message Request 行为。
在哪里配: CanNm -> CanNmChannelConfig_0 -> RMSTime / CanNmRepeatMessageTime(EB)
何时生效: CanNm 进入 Repeat Message 状态后生效。
注意: 只改 RepeatMessageTime 不等于打开节点发现。
    NodeDetection、RepeatMsgInd 等开关要另看。
    如果配置了NM 快发，RepeatMessageTime 必须大于：Number of immediate NM PDUs * Immediate NM PDU cycle time
    这是为了保证 immediate 快发序列能落在 Repeat Message 状态窗口内。
CanNmTime / CanNmTimeoutTime(EB)
含义: NM 网络管理超时。持续收不到有效 NM 活动后，状态机会往睡眠方向走。 当前: 1 s。
影响: 太短容易误判网络释放。 太长会延迟睡眠相关状态。
在哪里配: CanNm -> CanNmChannelConfig_0 -> CanNmTime / CanNmTimeoutTime(EB)
何时生效: 需要区分当前 CanNm 所在状态：
1. 当前在 Normal Operation：到期后，通常是重启 Timer，并可能报 CANNM_E_NETWORK_TIMEOUT。不会直接进入 ReadySleep
   从 NOS 进入 RMS 的关键条件是本节点已经释放网络请求
2. 当前在 ReadySleep：1s 内没有有效 NM 活动继续刷新 / 保持 NM Timeout Timer，会从 ReadySleep 进入 PrepareBusSleep。
   Network Release 使状态机从 Normal Operation 走向 ReadySleep；CanNmTimeoutTime 超时使 ReadySleep 继续走向 PrepareBusSleep。
当前结论：
   客户问“对端不发后多久认为网络释放”，不能只 CanNmTimeoutTime
   CanNmTimeoutTime = 1s 更准确表示：本节点已释放网络并处于 ReadySleep 后，如果 1s 内没有有效 NM 活动，则进入 PrepareBusSleep。
   它不等于最终睡眠时间，最终进入 BusSleep 还要继续叠加 CanNmWaitBusSleepTime，并受 ComM / CanSM / 本地 Network Request / 其它节点 NM 活动影响。
注意: 这个看的是 NM 超时，不是Tx confirmation timeout(下方)
WBSTime / CanNmWaitBusSleepTime(EB)
含义: Prepare Bus Sleep 等待时间。
当前: 5 s。
影响:太短可能对端还没同步睡眠。 太长会延迟总线进入睡眠。
在哪里配: CanNm -> CanNmChannelConfig_0 -> WBSTime / CanNmWaitBusSleepTime(EB)
何时生效: CanNm 进入 Prepare Bus Sleep 后开始计时。
注意:这是 NM 进入 BusSleep 前的等待。不是 EcuM 最终下电时间。
MsgTimeoutTime / CanNmMsgTimeoutTime(EB)
含义: 等待本节点 NM Tx Confirmation 的超时时间。
当前: 40 ms。
影响:太短可能误判发送失败。 太长会拖慢异常恢复。
在哪里配: CanNm -> CanNmChannelConfig_0 -> MsgTimeoutTime / CanNmMsgTimeoutTime(EB)
何时生效:
    本节点发出 NM PDU 后，等待 CanIf/CanDrv TxConfirmation。
注意: 它盯的是“我这帧 NM 发出去有没有确认”。 CanNmTime / CanNmTimeoutTime(EB) 盯的是“网络管理活动是否超时”。(上方单元格)

所以即使 CanNm 周期正确、ComM FullCom了、CanSM Controller STARTED了，如果 CanNm PDU Ref 或 CanIf HTH/HRH/Range/DLC 错了，NM 仍然可能收发不通。

7.6 功能开关

CANNM_PASSIVE_MODE_ENABLED / CanNmPassiveModeEnabled(EB)
打开: 节点只被动参与 NM，通常不主动发 NM。
关闭: 节点可以主动请求网络并发送 NM。
CANNM_COM_CONTROL_ENABLED / CanNmComControlEnabled(EB)
打开: 允许通过 Nm/ComM 控制 NM 通信使能。
关闭: 无法通过标准路径动态 Disable/Enable NM 通信。
CANNM_USER_DATA_ENABLED / CanNmUserDataEnabled(EB)
打开: 支持 Get/Set NM UserData API。
关闭: 不能使用 NM UserData API。
CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB)
打开: NM UserData 来自 COM I-PDU / 信号路径。
关闭: UserData 不走 COM 信号承载。
CANNM_BUS_LOAD_REDUCTION_ENABLED / CanNmBusLoadReductionEnabled(EB)
打开: 可用 MsgReducedTime 降低 NM 发送频率。
关闭: MsgReducedTime 即使配置也不生效。
CANNM_REMOTE_SLEEP_IND_ENABLED / CanNmRemoteSleepIndEnabled(EB)
打开: 能通知远端节点都准备睡眠。
关闭: 不产生 RemoteSleep indication。
CANNM_PN_SUPPORTED / CanNmPnSupported(EB)；PnEnabled / CanNmPnEnabled(EB)
打开: 启用 PN 信息过滤、EIRA/ERA、PN 唤醒相关行为。
关闭: PNC disabled，PN offset/length/mask 不生效。
CanNmCarWakeUpRxEnabled / CanNmCarWakeUpRxEnabled(EB)
打开:
    解析 NM PDU 的 Car WakeUp bit 并上报。
关闭:
    不解析 Car WakeUp。

8. Nm 配置项

第 8 章核心定位

Nm 是统一门面。即使系统里只有 CanNm，通常也会配置 Nm，因为上层不应该直接绑死某一种 BusNm。

ComM / App  -> Nm API  -> CanNm

如果以后换成 FrNm、UdpNm，或者一个 ECU 有多种 NM，总体接口仍然可以通过 Nm 抽象。

速查方式：先确认 Nm 通道是否正确桥接 ComM 和 CanNm；再看 UserData、StateChange、RemoteSleep、Coordinator 等开关是否按项目需要启用。
8.1 Nm 桥接关系
ComM Channel ESC_M
    -> Nm Channel ChassisCan1NmCluster
        -> CanNm Channel CanNmChannelConfig_0
NmComMChannelRef -> ComM Channel：
Nm 通道必须桥接到正确 ComM Channel，例如 ESC_M。
NmStandardBusType = NM_BUSNM_CANNM：该 Nm 通道下接 CanNm。

Nm 的核心职责：

1. 给 ComM 提供统一 NM API。
2. 把 Nm_NetworkRequest / Nm_NetworkRelease 转发给 CanNm。
3. 把 CanNm 的状态变化回调给上层。
4. 统一处理 UserData、RemoteSleep、Coordinator 等抽象能力。
8.2 StandardBusType / NmStandardBusType(EB)
当前: NM_BUSNM_CANNM
含义: 这个 Nm 通道下接的是 CanNm。

影响：

ComM 调 Nm_NetworkRequest()
    -> Nm 根据 BusNm 类型转发
        -> CanNm_NetworkRequest()

如果配错：

ComM 请求网络，但 Nm 转不到正确 BusNm。
表现可能是 ComM 状态看似变化，但 CanNm 不发 NM。
8.3 ComMChannelRef / NmComMChannelRef(EB)
当前: ESC_M
含义: Nm 通道绑定到 ComM 的 ESC_M 通道。
引用: ComM ESC_M   -> Nm ESC_M  -> CanNm
如果配错:ComM 的 FullCom 请求和 Nm/CanNm 不在同一条逻辑链路上。
可能出现 CanSM Controller 已经 STARTED，但 CanNm 不按预期请求网络。
8.4 NM_COM_CONTROL_ENABLED / NmComControlEnabled(EB)
当前:  true
含义:  允许通过 Nm/ComM 控制 NM 通信使能。
打开:  ComM / Nm 可以走标准接口控制 NM 通信行为。
关闭:  标准路径下动态控制 NM 通信能力受限。
排查点:客户说“ComM 已经请求 FullCom，但 NM 通信控制不起作用”，要看 NM_COM_CONTROL_ENABLED / NmComControlEnabled(EB) 和 CANNM_COM_CONTROL_ENABLED / CanNmComControlEnabled(EB) 是否一致。
8.5 NM_USER_DATA_ENABLED / NmUserDataEnabled(EB)
当前: true
含义: Nm API 层开放 UserData 能力。
注意:NM_USER_DATA_ENABLED / NmUserDataEnabled(EB) = true 只是 Nm 抽象层允许 UserData。
CANNM_USER_DATA_ENABLED / CanNmUserDataEnabled(EB) 也要打开，CanNm 层才真正支持。
还要区分两条路线:
API 路线:  Nm / CanNm UserData API 设置用户数据。
COM 信号路线: COM I-PDU / Signal 填 NM UserData。
需要 CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB) = true。
8.6 NM_STATE_CHANGE_IND_ENABLED / NmStateChangeIndEnabled(EB)
当前: true
含义: Nm 状态变化可以通知上层。
排查: 客户说“上层收不到 NM 状态变化”，不要只看 CanNm。
要同时查：
    NM_STATE_CHANGE_IND_ENABLED / NmStateChangeIndEnabled(EB)
    CANNM_STATE_CHANGE_IND_ENABLED / CanNmStateChangeIndEnabled(EB)
    BswM / RTE 回调配置
    上层 callback 是否生成
8.7 NM_COORDINATOR_SUPPORT_ENABLED / NmCoordinatorSupportEnabled(EB)
当前:  false
含义:  当前不是 NM Coordinator，不做多网络协调睡眠。

打开后影响：

8.9 Nm 常用 API 按方向理解 Nm 的接口按方向分三类：上层主动调用、BusNm 状态上报、查询/数据类接口。

上层主动调用：

Nm_NetworkRequest(Channel)
    上层请求网络。 通常由 ComM 在 FullCom Network Requested 时调用。 Nm 再转发到 CanNm_NetworkRequest。
Nm_NetworkRelease(Channel)
    上层释放网络。 通常由 ComM 在没有用户保持通信时调用。 Nm 再转发到 CanNm_NetworkRelease。
Nm_PassiveStartUp(Channel)
    被动启动网络管理。 常用于检测到网络活动后，让 NM 进入网络相关状态，但不一定代表本节点主动请求网络。

通信控制类：

Nm_EnableCommunication(Channel)
    关闭指定 NM Channel 的 NM PDU 发送能力。停止该通道继续发送 NM 报文。只控制NM报文
Nm_DisableCommunication(Channel)
    恢复指定 NM Channel 的 NM PDU 发送能力。允许该通道重新发送 NM 报文。只控制NM报文
注意：是否可用要看 NM_COM_CONTROL_ENABLED / NmComControlEnabled(EB) 和 CANNM_COM_CONTROL_ENABLED / CanNmComControlEnabled(EB)。 如果配置关闭，接口可能不可用或不起预期作用。

UserData 类：

Nm_SetUserData(Channel, data)/ Nm_GetUserData(Channel, data)/ Nm_GetPduData(Channel, data)
含义：设置或读取 NM UserData / NM PDU 数据。
是否可用要看 NM_USER_DATA_ENABLED / NmUserDataEnabled(EB)、CANNM_USER_DATA_ENABLED / CanNmUserDataEnabled(EB)。
如果希望 UserData 由 COM 信号填，还要看 CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB)。

状态查询类：

Nm_GetState(Channel, &state, &mode)
Nm_GetBusSynchronizationStatus(Channel, &status)
Nm_CheckRemoteSleepIndication(Channel, &status)
含义： 用于确认 NM 当前状态、同步状态、远端睡眠指示。是否有完整能力取决于对应开关和供应商实现。
8.10 Nm / CanNm / ComM 的调用方向
请求网络方向：App / DCM / BswM
    -> ComM_RequestComMode(...) -> ComM 决策是否 FullCom
          -> Nm_NetworkRequest()
              -> CanNm_NetworkRequest()
释放网络方向：
所有 ComM User释放/DCM InactiveDiagnostic/没有PNC和BswM保持
     -> ComM 判断可释放
         -> Nm_NetworkRelease()
             -> CanNm_NetworkRelease()
状态上报方向：
CanNm 状态变化 -> Nm 抽象层 -> ComM/ BswM/ RTE/ 应用回调
常见上报语义：
Network Start Indication  = 睡眠中收到 NM，网络被别人拉起
Network Mode              = NM 已进入网络模式；
Prepare Bus Sleep Mode    = 正在准备睡眠；
Bus Sleep Mode            = 已进入最终睡眠模式；
Remote Sleep Indication   = 其它节点都准备睡；
Remote Sleep Cancellation = 其它节点准备睡的状态被取消；
State Change Notification = 底层 NM 状态变化明细上报。
注意：CanNm 状态变化先到 Nm，再通知 ComM/BswM/RTE。
8.13 Nm 章节注意事项
1. Nm 是抽象层，不是 CanIf。
   CAN ID、HRH、HTH 不在 Nm 配。
2. Nm 是抽象层，不是 CanSM。
   Controller Start/Stop/Sleep 不在 Nm 配。
3. Nm 是抽象层，不是 ComM。
   是否允许 FullCom、是否被 NoWakeup/NoCom 阻塞，由 ComM 决策。
4. Nm 配错 Ref，会让 ComM、CanNm 不在一条链路上。
   表现可能像 CanNm 不工作，但根因是绑定错。
5. 只打开 NM_USER_DATA_ENABLED / NmUserDataEnabled(EB) 不够。
   CANNM_USER_DATA_ENABLED / CanNmUserDataEnabled(EB)、CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB) 路线也要确认。
6. 只打开 NM_STATE_CHANGE_IND_ENABLED / NmStateChangeIndEnabled(EB) 不够。
   CanNm 状态通知、BswM/RTE callback 也要确认。

8.12 Nm 常见故障定位

ComM 请求了，但 CanNm 不发 NM：

1. ComMChannelRef / NmComMChannelRef(EB) 是否指向 ESC_M。
2. StandardBusType / NmStandardBusType(EB) 是否为 NM_BUSNM_CANNM。
3. Nm 是否真的转发到 CanNm。
4. CanNm 通道是否与同一个 ComM Channel 对齐。
5. CanSM Controller 是否已经 STARTED。

上层收不到 NM 状态变化：

1. NM_STATE_CHANGE_IND_ENABLED / NmStateChangeIndEnabled(EB) 是否 true。
2. CANNM_STATE_CHANGE_IND_ENABLED / CanNmStateChangeIndEnabled(EB) 是否 true。
3. BswM / RTE callback 是否配置。
4. 上层是否注册或生成了对应回调。
5. CanNm 状态是否真的发生变化。

UserData 设置/读取不生效：

1. NM_USER_DATA_ENABLED / NmUserDataEnabled(EB) 是否 true。
2. CANNM_USER_DATA_ENABLED / CanNmUserDataEnabled(EB) 是否 true。
3. 是否误以为 CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB)=true。
4. 当前 DF_XY CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB)=false，所以不是 COM 信号自动填。

RemoteSleep 没有通知：

1. NM_REMOTE_SLEEP_IND_ENABLED / NmRemoteSleepIndEnabled(EB) 是否 true。
2. CANNM_REMOTE_SLEEP_IND_ENABLED / CanNmRemoteSleepIndEnabled(EB) 是否 true。
3. 对端节点是否真的进入远端睡眠条件。
4. BswM/RTE 是否配置接收该通知。

Coordinator 行为没有出现：

1. NM_COORDINATOR_SUPPORT_ENABLED / NmCoordinatorSupportEnabled(EB) 当前是 false。
2. 当前项目不要按 Coordinator 逻辑解释睡眠。
3. CBV 的 Coordinator Sleep Ready 位当前通常不是主线逻辑。
8.14 Nm 客户话术翻译
“ComM 请求了，但 NM 没反应”
    查 ComMChannelRef / NmComMChannelRef(EB)、StandardBusType / NmStandardBusType(EB)、CanNm channel ref、CanSM Started。
“上层收不到 NM 状态变化”
    查 NM_STATE_CHANGE_IND_ENABLED / NmStateChangeIndEnabled(EB)、CANNM_STATE_CHANGE_IND_ENABLED / CanNmStateChangeIndEnabled(EB)、BswM/RTE 回调。
“为什么没有 RemoteSleep”
    查 NM_REMOTE_SLEEP_IND_ENABLED / NmRemoteSleepIndEnabled(EB)、CANNM_REMOTE_SLEEP_IND_ENABLED / CanNmRemoteSleepIndEnabled(EB)、对端状态。
“UserData API 不生效”
    查 NM_USER_DATA_ENABLED / NmUserDataEnabled(EB)、CANNM_USER_DATA_ENABLED / CanNmUserDataEnabled(EB)、CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB)。
“这个项目是不是 Coordinator”
    查 NM_COORDINATOR_SUPPORT_ENABLED / NmCoordinatorSupportEnabled(EB)。当前 DF_XY = false。
8.15 Nm 章节口诀
Nm 不决定 Controller 是否 Start。
Nm 不直接配置 CAN ID。
Nm 是 ComM 和 CanNm 中间的统一 API 门面。
ComM 要网络:
    ComM -> Nm_NetworkRequest -> CanNm_NetworkRequest
ComM 释放网络:
    ComM -> Nm_NetworkRelease -> CanNm_NetworkRelease
CanNm 状态变化:
    CanNm -> Nm callback -> ComM / BswM / RTE
