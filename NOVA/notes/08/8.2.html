2. 通路总图

2.1 模式控制分支

ComM Channel ESC_M
    -> CanSM Network ESC_M
        -> CAN Controller ESC_M
        -> CAN Controller ESC_S

含义：

ComM 对 ESC_M 请求 FullCom/NoCom。
CanSM 的 ESC_M Network 收到请求后，可以一起控制下面挂的两个 Controller。

注意：

CanSM 控制两个 Controller = 可以 Start/Stop/Sleep 两个 Controller。
不等于 CanNm 的一帧 NM 报文自动发到两个 Controller。

NM 报文到底走哪个 Controller，要看：

TxPduId / CanNmTxPduRef(EB)
    -> CanIf Tx PDU
        -> HTH -> 对应哪个 CAN Controller
RxPduId / CanNmRxPduRef(EB)
    -> CanIf Rx PDU / HRH / CAN ID Range
        -> 对应哪个 CAN Controller

2.2 NM 协议分支

ComM Channel ESC_M
    -> Nm Channel ChassisCan1NmCluster
        -> CanNm Channel CanNm_ChanConfig / CanNmChannelConfig_0(EB)
            -> CanIf NM Tx/Rx PDU

含义：

ComM 创建/配置一个逻辑通信通道 ESC_M。 Nm、CanNm、CanSM 都引用这个 ComM Channel。 这样它们就串成同一条通信管理链路。

3. 一个 CanSM Network 管两个 Controller

当前项目配置：

CanSM Network Name = ESC_M
ComM Channel = /ComM/ComM/ComMConfigSet/ESC_M
List of CAN Controllers = ESC_M / ESC_S

结论：

一路 ComM Channel ESC_M -> 控制一个 CanSM Network ESC_M -> 这个 CanSM Network 管两个 Controller

什么时候一路 ComM 就够：

两个 Controller 总是一起醒、一起睡。
两个 Controller 属于同一个逻辑通信通道。
应用不需要分别控制它们。客户需求也不要求一个开、一个关。

什么时候必须拆两路 ComM：

两个 Controller 要独立睡眠/唤醒。
一个 Controller 通信时，另一个不应该被带起来。
两个 CAN bus 有不同 NM 报文。
两个网络有不同 ComM 用户、不同诊断、不同 BusOff 策略。客户要求分开控制。

判断口诀：

不是“两个 Controller 就必须两个 ComM”。
而是“独立通信控制需求 = 独立 ComM Channel / CanSM Network / Nm / CanNm”。

10. CanSM 配置项

第 10 章核心定位

CanSM 是 CAN State Manager。它不负责 NM 报文内容，它负责把 ComM 的通信模式请求落到 CAN Controller 状态。

ComM
    -> CanSM_RequestComMode(Network, mode)
        -> CanSM
            -> CanIf / CanDrv / CanTrcv
                -> Controller STARTED / STOPPED / SLEEP
ComM 决定要不要通信。
CanSM 执行 CAN Controller 怎么切。
CanNm 决定 NM 报文怎么发。
CanIf 决定 PDU 走哪个 Controller/HRH/HTH。
10.1 CanSM 在链路里的位置

当前项目：

ComM Channel:
    ESC_M
CanSM Network:
    ESC_M
ComMChId / CanSMComMNetworkHandleRef(EB):
    ESC_M
CanSM Controllers:
    ESC_M
    ESC_S

含义：

ComM 的 ESC_M 通道请求 FullCom / SilentCom / NoCom。
CanSM 的 ESC_M Network 收到请求。
这个 CanSM Network 负责控制 ESC_M 和 ESC_S 两个 CAN Controller。

注意：

一个 CanSM Network 管两个 Controller，只代表模式控制一起管。
不代表 NM 报文自动复制到两个 Controller。
NM 报文走哪个 Controller，要看 CanIf Tx PDU 的 HTH 和 Rx PDU 的 HRH。
10.2 ComMChId / CanSMComMNetworkHandleRef(EB)
当前:
    ESC_M
含义:
    CanSM Network 绑定 ComM Channel。

影响：

ComM 请求 ESC_M FullCom
    -> CanSM 找到 ESC_M Network
        -> 控制该 Network 下的 Controller

如果配错：

ComM 请求模式时找不到正确 CAN Network。
表现可能是 ComM 状态在变，但 Controller 不按预期 STARTED/STOPPED。

排查：

FullCom 请求存在，但 Controller 不起来：
    先查 ComMChId / CanSMComMNetworkHandleRef(EB) 是否指向 ESC_M。
10.3 CtrlRef / CanSMController(EB) List
当前: ESC_M 和 ESC_S

含义：

CanSM Network ESC_M 下挂两个 CanIf Controller。
ComM 对 ESC_M 的模式请求，会由 CanSM 应用到这两个 Controller。

什么时候这样配合理：

两个 Controller 总是一起醒、一起睡。
两个 Controller 属于同一个逻辑通信域。
客户不要求独立控制。

什么时候不合理：

一个 Controller 要能单独睡，另一个保持通信。
两个 Controller 有不同 NM。
两个 Controller 有不同诊断通道。
两个 Controller 有不同 BusOff 策略或安全策略。

判断口诀：

控制需求一起走，就放一个 CanSM Network。
控制需求要拆开，就拆 ComM Channel / CanSM Network / Nm / CanNm。
10.4 CanSM 三个通信模式怎么落地

FullCom：

ComM -> CanSM_RequestComMode(FULL)
CanSM -> CanIf_SetControllerMode(STARTED)
CanSM -> CanIf_SetPduMode(ONLINE) 或供应商等效处理

效果：

可收可发。CanNm 能发 NM。CanTp/DCM 可以诊断。普通报文也有通信

SilentCom：

ComM -> CanSM_RequestComMode(SILENT)
CanSM -> Controller 通常保持可接收，Tx 方向受限

效果：

通常可收不可发。 DCM 可能收得到请求，但响应发不出去。

NoCom：

ComM -> CanSM_RequestComMode(NO_COMM)
CanSM -> CanIf_SetControllerMode(STOPPED / SLEEP)
CanSM -> PDU mode OFFLINE

效果：

该 CAN 通道无法正常收发。DCM、CanTp、CanNm、普通报文都受影响。
10.5 CanSMModeRequestRepetitionMax / Time
ModeReqRepMax / CanSMModeRequestRepetitionMax(EB) = 10
ModeReqRepTime / CanSMModeRequestRepetitionTime(EB) = 0.005 s

含义：

CanSM 请求 CanIf/CanDrv 切 Controller 模式时，如果一次没成功，会重试。 最多重试 10 次。 每 5ms 重试一次。

影响：

重试太少:     瞬态失败时容易直接进入错误处理。
重试太多:     控制器确实异常时，状态切换会拖更久。
重试周期太短: 压力更大，但响应更快。
重试周期太长: 模式切换变慢。
ComM 请求 FullCom 后 Controller 起不来：
    查 CanSM 是否在重复请求。
    查 CanIf_SetControllerMode 返回值。
    查 CanIf_ControllerModeIndication 是否回来。
10.7 CanSM PN 配置

当前：

CANSM_PNSUPPORT / CanSMPNSupport(EB) = false
CANSM_PARTIALNETWORKING / CanSMActivatePN(EB) = false

含义：CanSM 当前不参与 PN 唤醒链路。

如果客户要求 PNC / Selective Wake：

不能只打开 CANSM_PARTIALNETWORKING / CanSMActivatePN(EB)
还要同步检查：
    COMM_PNC_SUPPORT / ComMPncSupport(EB) / PncEnabled / ComMPncEnabled(EB)
    CANNM_PN_SUPPORTED / CanNmPnSupported(EB)；PnEnabled / CanNmPnEnabled(EB)
    CANIF_PUBLIC_PN_SUPPORT / CanIfPublicPnSupport(EB)
    Com/PduR EIRA/ERA
    BswM rules
    CanTrcv selective wake 能力
10.10 CanSM 章节口诀
CanSM 管 Controller，不管 NM 报文字节。
CanSM 响应 ComM 模式请求，不自己决定业务要不要通信。
CanSM 可一个 Network 管多个 Controller，但 PDU 走哪个 Controller 由 CanIf 决定。
BusOff 恢复参数在 CanSM，不在 CanNm。
PN 要端到端打开，不能只开 CanSM。
10.6 CanSM BusOff Recovery：参数、逻辑和排查

BusOff 恢复参数配置在 CanSM，不在 CanNm。BusOff 是 Controller / CanSM / CanIf / CanDrv 层的问题。

CanSM -> CAN Network -> ESC_M -> General
参数当前值作用调参影响
BorCounterL1ToL2 / CanSMBorCounterL1ToL2(EB)5BusOff 恢复先走 L1；连续 BusOff/恢复失败达到阈值后进入 L2。值越小，越快进入慢恢复；值越大，越久停留在快恢复。总线严重异常时太大可能反复冲击总线。
BorTimeL1 / CanSMBorTimeL1(EB)0.5 sL1 阶段 BusOff 后等待 0.5s 再尝试恢复 Controller。短则恢复快，但异常未消失时容易反复 BusOff；长则更保守但恢复慢。
BorTimeL2 / CanSMBorTimeL2(EB)2.0 s连续 BusOff 进入 L2 后，每次恢复等待 2s。L2 比 L1 慢，用来处理连续 BusOff 或严重总线异常。
BorTimeTxEnsured / CanSMBorTimeTxEnsured(EB)1.0 sController 恢复后观察 1s，稳定后 CanSM 才认为恢复可靠。太短可能误判恢复稳定；太长会延迟回到正常通信状态。
BOR Tx Confirmation Polling未勾选当前没有打开 Tx Confirmation 轮询确认方式。是否依赖 Tx confirmation 判断恢复，要看供应商 CanSM 实现和其他配置。
CANSM_PROD_ERR_HANDLING_BUS_OFF / CanSMBusOffReportToDem(EB) / CANSM_E_BUS_OFFDEMBusOff 事件会上报 DEM。如果 DEM event/mapping 没配好，可能 CanSM 检测到 BusOff，但诊断事件看不到。

恢复逻辑

BusOff 发生
    -> CanSM 收到 ControllerBusOff
        -> 进入 BOR
            -> L1 快恢复，等待 CanSMBorTimeL1
                -> 如果连续失败达到 CanSMBorCounterL1ToL2
                    -> 进入 L2 慢恢复，等待 CanSMBorTimeL2
                        -> Controller 恢复后观察 CanSMBorTimeTxEnsured
                            -> 稳定后回正常通信

客户话术怎么翻译

客户说法主查配置不能忽略的非配置原因
BusOff 恢复太慢CanSMBorTimeL1、CanSMBorTimeL2、CanSMBorCounterL1ToL2、CanSMBorTimeTxEnsured先确认是不是连续 BusOff 已进入 L2，而不是单纯 L1 慢。
BusOff 一直反复不要只把恢复时间调短优先查物理层、波特率、采样点、终端电阻、CAN ID 冲突、发送周期、BusLoad、ACK。
BusOff 没有 DTCCanSMBusOffReportToDem / CANSM_E_BUS_OFF查 DEM event、event mapping、CanSM BusOff 回调是否进来。
10.9 CanSM 常见故障定位

ComM FullCom 请求后 Controller 不 STARTED：

1. ComM 是否真的请求 FullCom。
2. ComMChId / CanSMComMNetworkHandleRef(EB) 是否绑定正确。
3. CanSM Controller list 是否包含目标 Controller。
4. CanIf_SetControllerMode 是否返回成功。
5. ControllerModeIndication 是否回来。
6. ModeRequestRepetition 是否已耗尽。

Controller STARTED 但 NM 不发：

1. COMM_NM_VARIANT_OF_CHANNEL / ComMNmVariant(EB) 是否 FULL。
2. Nm_NetworkRequest 是否调用。
3. CanNm 是否 Network Requested。
4. CanNmTxPduRef / CanIf Tx PDU / HTH 是否正确。

Controller STARTED 但诊断不通：

1. ComM 当前是否 FullCom 而不是 SilentCom。
2. CanIf PDU mode 是否 ONLINE。
3. CanTp / PduR / DCM 路由是否正确。
4. DCM 会话、安全、寻址是否正确。

BusOff 恢复异常：

1. CanSM 是否收到 BusOff indication。
2. L1/L2 参数是否符合客户要求。
3. 是否上报 DEM。
4. 是否反复 BusOff。
5. 物理层和总线负载是否异常。
