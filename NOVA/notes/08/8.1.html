1. 总体心智模型

这几层不要混：

DCM: 管诊断协议本身，例如 UDS 会话、服务、S3 超时、诊断请求/响应。
ComM: 管通信模式。决定某个通信通道是 NoCom、SilentCom 还是 FullCom。
CanSM :管 CAN 控制器状态。把 ComM 的模式请求变成 CanIf/CanDrv/CanTrcv 的 Start、Stop、Sleep。
Nm: NM 抽象层。ComM 通常通过 Nm API 管网络，不直接绑死 CanNm。
CanNm: CAN NM 协议层。负责 NM 报文收发、Repeat、Normal、ReadySleep、PrepareBusSleep、BusSleep。
CanIf: CAN 接口层。负责 CAN ID、PDU、HRH/HTH、上层回调，把 NM 报文送到 CanNm。

一句话：

DCM 管诊断，ComM 管通信授权，CanSM 管控制器，Nm 做抽象，CanNm 跑 NM 协议，CanIf 接 CAN 报文。

5. DCM 通过 ComM 保持/释放通信

核心结论DCM 不解析/发送 NM，也不直接控制 CAN Controller；诊断保通靠 ComMDcmUsage、DCM Channel Ref、ComM_DCM_ActiveDiagnostic / InactiveDiagnostic 三件套，最终由 ComM 保持 FullCom，CanSM 维持 Controller STARTED。

5.1 DCM 保持通信用什么接口

场景接口/路径含义排查抓手
诊断开始/诊断活跃ComM_DCM_ActiveDiagnostic(Channel)DCM 通知 ComM：该通道有诊断活动，需要保持通信。诊断中掉线，先确认这个接口是否被 DCM 调用、Channel 是否正确。
诊断结束/不再活跃ComM_DCM_InactiveDiagnostic(Channel)DCM 释放诊断保持；如果没有 App/BswM/PNC 等其他请求，ComM 才能往释放方向走。诊断结束后不睡，确认 Inactive 是否调用，或是否还有其他 FullCom 请求源。
ComM 保持 FullComComM 内部请求聚合DCM 活跃只是 FullCom 请求源之一；最终还要看 inhibition、CommunicationAllowed、User/Channel 映射。查 ComM_GetCurrentComMode、ComM_GetRequestedComMode、ComM_GetMaxComMode。
Controller 保持可通信ComM -> CanSM -> CanIf/CanDrvCanSM 把 ComM 模式请求落到 CAN Controller STARTED/STOPPED/SLEEP。FullCom 有但诊断发不出，继续查 CanSM mode indication、CanIf PDU mode、CanTp/PduR/DCM 路由。

5.3 FullCom / SilentCom / NoCom 对诊断的影响

通信模式诊断表现注意点
FullCom通常可收可发，DCM 可以正常收请求、发响应。如果仍不通，查 CanTp/PduR/DCM 路由、ID、寻址方式、会话/安全/S3。
SilentCom不主动发送通信，接收路径通常仍可用；诊断可能收到请求但响应/FlowControl 发不出去。具体行为还要结合 CanIf PDU mode、BswM 策略和供应商实现确认。
NoComController/Transceiver 可能 Stop 或 Sleep，诊断通道不可通信。先查 ComM 是否被限制到 NoCom，CanSM 是否把 Controller 拉起。

6. ComM FullCom 阻塞速查

排查原则FullCom 起不来，不要一上来就怀疑 CanSM。先确认“请求源有没有到 ComM”，再看“ComM 有没有被限制”，最后看“ComM 请求有没有传到 CanSM / Nm / CanNm / CanIf”。

6.0 ComM 三值和映射速查

User -> Channel 映射口径
ComM_RequestComMode(User, FULL)：传入的是 User，不是 Channel；用户请求的 Mode 只接受 COMM_FULL_COMMUNICATION 或 COMM_NO_COMMUNICATION，不能请求 COMM_SILENT_COMMUNICATION。
ComM 根据配置里的 User -> Channel 映射，把请求落到一个/多个 ComMChannel。
位置/关键词：ComM -> ComMConfigSet -> ComMUser / ComMChannel / UserPerChannel；ComMUserChannelRef、ComMChannelRef、User / Channel Mapping。
生成代码搜索：ComM.xdm、ComM_Cfg.h/.c、ComM_Lcfg.c、ComM_PBcfg.c；搜 ESC_M、ComMUser、UserToChannel、ChannelToUser、UserPerChannel。
典型现象：User Handle 或映射错：接口调用正常，但目标 Channel / Controller 不动。
Requested / Max / Current 三值
接口/值判断异常指向
ComM_GetRequestedComMode(User,&mode)想不想请求源、User Handle、释放过早。
ComM_GetMaxComMode(User,&mode)允不允许NoCom、NoWakeup、Limit、CommunicationAllowed、PreventWakeUp。
ComM_GetCurrentComMode(User,&mode)实际到没到CanSM 执行、Nm/CanNm、CanIf PDU mode。
组合判断 / Limit 解除
Req=FULL，Max=NO，Cur=NO：
请求到了，但被限制压住，先查 limitation / inhibition。
Req=FULL，Max=FULL，Cur≠FULL：
ComM 允许了，继续查 CanSM、Nm、CanIf。
Req=NO，Max=FULL，Cur=FULL：
可能其他 User / DCM / BswM 保持，或 ComMTMinFullComModeDuration 未到。
解除 NoCom limitation：
ComM_LimitChannelToNoComMode(Channel, FALSE)//Channel分闸
ComM_LimitECUToNoComMode(FALSE)            // ECU 总闸
Max=NO 时可以调用 FALSE；若仍 NO，继续查 CommunicationAllowed、PreventWakeUp、NoWakeup、BswM/EcuM 是否又置位、User/Channel 是否查错。

6.1 FullCom 阻塞总表

层级阻塞点典型现象重点检查怎么恢复/验证
请求源User 没请求到目标 ChannelApp/DCM/BswM 以为请求了，目标 CAN 通道不动。ComM_RequestComMode(User, COMM_FULL_COMMUNICATION)；User 是否映射到 ESC_M；User Handle 是否用错。用 ComM_GetRequestedComMode 看 User 请求；确认 User -> Channel Mapping。
运行时门控ComM_CommunicationAllowed(Channel, FALSE)User 请求 FullCom，但 ComM 不允许真正拉起通道。BswM/EcuM/系统模式管理是否在初始化、睡眠、运输模式、低功耗策略里置 FALSE。确认合适时机调用 ComM_CommunicationAllowed(Channel, TRUE)；看 ComM 当前模式是否开始推进。
静态/运行时限制NoCom 限制GetMaxComMode 可能被压到 NoCom；FullCom 请求被压住。ComMNoCom；ComM_LimitChannelToNoComMode；ComM_LimitECUToNoComMode。配置项不需要强制 NoCom 时保持 false；运行时限制要调用 FALSE 解除。
唤醒抑制NoWakeup / PreventWakeUp睡眠态或低功耗态有请求，但通道不被拉起。ComMNoWakeup；ComM_PreventWakeUp；ComMWakeupInhibitionEnabled；ComM_GetInhibitionStatus。确认 PreventWakeUp 是否被 BswM/EcuM/应用置位；按策略解除。
DCM 保持诊断没有成为 FullCom 请求源诊断中掉通信，或者诊断结束后行为不符合预期。COMM_DCM_ENABLED / ComMDcmUsage(EB) 是否 true；DCM 是否调用 ComM_DCM_ActiveDiagnostic / InactiveDiagnostic；DCM Channel Ref 是否正确。诊断中抓接口调用/ComM 请求源；诊断结束后确认 Inactive 是否释放。
PNC/同步唤醒PNC 或同步唤醒策略影响 FullCom某些功能请求能保持网络，另一些不能；或一个通道被另一路带起。ComMPncSupport、PNC mapping、EIRA/ERA、ComMSynchronousWakeUp、BswM rules。当前 DF_XY PNC 关闭时，不应把 FullCom 异常优先归因于 PNC。
ComM 到 CanSMCanSM 网络引用错/Controller 起不来ComM 状态有变化，但 Controller 没 STARTED。CanSMComMNetworkHandleRef；CanSMController 列表；CanIf_SetControllerMode；Controller mode indication。确认 CanSM Network 绑定 ESC_M；确认 ESC_M/ESC_S Controller 是否按需求一起 Start。
ComM 到 Nm/CanNmNm/CanNm 引用不在同一逻辑通道FullCom 看似起来，但 NM 不请求/不发。NmComMChannelRef；CanNmComMNetworkHandleRef；ComMNmVariant = FULL。确认 ComM ESC_M、Nm Channel、CanNm Channel 绑定一致。
CanNm 到 CanIfNM PDU 路由或 HTH/HRH 错Controller STARTED，CanNm 状态也对，但总线上没有 NM，或收不到 NM。CanNmTxPduRef / RxPduId / CanNmRxPduRef(EB)；CanIf Tx/Rx PDU；HTH/HRH；CAN ID / Range / DLC。Trace 看总线；再查 CanIf TxConfirmation / RxIndication 是否进 CanNm。

6.2 现场排查顺序

1. 先看 ComM User 请求：RequestedMode / CurrentMode / MaxMode。
2. 再看 inhibition：NoCom、NoWakeup、CommunicationAllowed、PreventWakeUp。
3. 再看 CanSM：ComM 请求是否传到 CanSM，Controller 是否 STARTED。
4. 再看 Nm/CanNm：FULL NM 是否触发 Nm_NetworkRequest / CanNm_NetworkRequest。
5. 最后看 CanIf：TxPduRef/RxPduRef、HTH/HRH、CAN ID、DLC、TxConfirmation、RxIndication。

6.3 这章要记住的判断

ComM 是“请求聚合 + 模式裁决”。CanSM 是“Controller 模式执行”。CanNm 是“NM 协议状态机和 NM 报文”。FullCom 不起来时，只有确认 ComM 没被限制、CanSM 没执行失败之后，才进入 CanNm/CanIf 方向排查。

9. ComM 配置项

第 9 章核心定位

ComM 是通信模式经理。它不解析 NM 报文，也不解析诊断报文，但它决定一个通信通道当前允许什么通信模式。

ComM User 请求 / DCM 诊断活跃 / BswM 和 EcuM 通信允许 / 模式限制 和 唤醒抑制 / PNC 请求
    -> ComM 统一决策   -> 指挥CanSM 切 Controller 模式  -> 指挥Nm/CanNm 请求或释放网络
速查方式：ComM 问题优先按“请求源 → 限制/抑制 → CanSM 执行 → Nm/CanNm 网络管理”顺序排查，不要直接跳到底层 CAN。
9.1 ComM 的两个核心对象：User 和 Channel
ComM Channel：逻辑通信通道，例如 ESC_M；
后续绑定 CanSM Network、Nm Channel、CanNm Channel。
ComM User：通信请求源，例如 App / DCM / BswM 相关用户；
User 通过配置映射到 Channel。
映射规则：一个 User 可映射一个或多个 Channel；
请求只影响其映射到的 Channel。

配置/生成代码查点：

EB 位置：
ComM -> ComMConfigSet -> ComMUser / ComMChannel / UserPerChannel。
常见字段：
ComMUserChannelRef、ComMChannelRef、User / Channel Mapping。
搜索关键词：
ESC_M、ComMUser、UserToChannel、ChannelToUser、UserPerChannel、ComMChannelRef。
9.2 COMM_NM_VARIANT_OF_CHANNEL / ComMNmVariant(EB)
当前: FULL
含义: ComM 使用真实 Nm/CanNm 网络管理。

FULL 时的动作：

请求通信:
    ComM -> CanSM_RequestComMode(FULL)
    ComM -> Nm_NetworkRequest()
    Nm -> CanNm_NetworkRequest()
    CanNm 发 NM
释放通信:
    ComM -> Nm_NetworkRelease()
    CanNm 走 ReadySleep / PrepareBusSleep / BusSleep
    ComM -> CanSM_RequestComMode(NO_COMM)

和其他模式对比：

NONE:     没有 NM。
LIGHT:    轻量管理，不跑完整 NM 协议。
PASSIVE:  有 NM，但节点通常不主动请求网络。
FULL:     完整 NM，可主动请求和释放网络。
9.5 COMM_T_MIN_FULL_COM_MODE_DURATION / ComMTMinFullComModeDuration(EB)
当前:  5.0 s
含义:  ComM 进入 FullCom 后至少保持 5s。

作用：

防止刚进入 FullCom 又立刻释放，导致网络抖动。

注意：

这个时间属于 ComM 层。
9.6 COMM_SYNCHRONOUS_WAKE_UP / ComMSynchronousWakeUp(EB)
当前: true
含义: 同步唤醒相关通道。

影响：

多COMM通道项目中，一个通道唤醒可能带动相关通道一起进入通信准备

注意：

客户说“为什么这个通道被一起带起来”，要查 SynchronousWakeUp、PNC、BswM rules、Channel mapping。
9.7 COMM_DCM_ENABLED / ComMDcmUsage(EB)
当前: true
含义: DCM 可以通过 ComM 保持通信。

典型接口：

ComM_DCM_ActiveDiagnostic(Channel)
ComM_DCM_InactiveDiagnostic(Channel)

影响：

ActiveDiagnostic:  诊断活跃，ComM 保持 FullCom。
InactiveDiagnostic:诊断结束，ComM 在没有其他请求时释放通信。

注意：

诊断保持通信不等于 CanNm timer。
这是 DCM 通过 ComM 持有 FullCom。
9.8 NoCom / ComMNoCom(EB)
当前:  false
含义:  如果 true，该通道被限制在 NoCom。

影响：

ComM User 请求 FullCom 可能被压住。
DCM 也无法通过该通道正常诊断。

相关接口：

ComM_LimitChannelToNoComMode(Channel, TRUE/FALSE)

ComM_LimitECUToNoComMode(TRUE/FALSE)

ComM_GetMaxComMode(User, &mode)
9.9 NoWakeup / ComMNoWakeup(EB)
当前:  false
含义:  如果 true，禁止通过该通道唤醒通信。

影响：

请求 FullCom 不一定能把通道从低功耗拉起来。

相关接口：

ComM_PreventWakeUp(Channel, TRUE/FALSE)


ComM_GetInhibitionStatus(Channel, &status)
9.10 Mode Limitation 和 Wakeup Inhibition
Mode Limitation：
作用:  允许运行时限制某通道或整个 ECU 到 NoCom。
接口:
    ComM_LimitChannelToNoComMode(Channel, TRUE/FALSE)
    ComM_LimitECUToNoComMode(TRUE/FALSE)
Wakeup Inhibition：
作用:  允许运行时阻止某通道唤醒。
接口:
     ComM_PreventWakeUp(Channel, TRUE/FALSE)
FullCom 请求失败时，不要只看 CanSM。 查：
    User 请求是否存在
    User 是否映射到 Channel
    ComM_CommunicationAllowed和CommunicationAllowed     gate(API) 是否为 TRUE
    NoCom / NoWakeup 是否置位
    PreventWakeUp 是否置位
    LimitChannelToNoCom / LimitECUToNoCom 是否置位
    DCM 是否 ActiveDiagnostic

当前:  false / false
含义:  当前 ComM 不处理 PNC。
打开后：ComM 要处理 PNC ID、PNC 与 Channel/User 映射、EIRA/ERA 信号。

9.12 ComM 三种通信模式
COMM_NO_COMMUNICATION
含义：
通道不通信。
CanSM 可能把 Controller Stop/Sleep。
DCM、CanTp、普通 CAN 报文都无法通过这个 CAN 通道正常通信。
典型场景：
没有任何用户请求通信。
DCM 不活跃。
ComM 允许释放。
Nm/CanNm 进入睡眠相关状态。
COMM_SILENT_COMMUNICATION
含义：
通常可收不可发。
适合某些只监听、不发送的中间状态或限制状态。
对DCM影响：
可能收到诊断请求，但响应发不出去。
UDS 多帧尤其有问题，因为 FlowControl / Response 都需要发送。COMM_FULL_COMMUNICATION
含义：
可收可发。CanSM Controller 应处于 STARTED。
DCM、CanTp、普通通信、NM 都具备通信基础。
注意：
FullCom 只是底层通道具备通信条件。
诊断是否响应还要看CanTp/PduR/DCM 路由、会话、安全、服务支持
9.13 ComM FULL NM 状态粗流程

请求通信：

NoCom
    -> User 请求 FullCom / DCM Active / PNC 请求
        -> ComM 判断允许通信
            -> CanSM_RequestComMode(FULL)
                -> Controller STARTED
            -> Nm_NetworkRequest
                -> CanNm 发 NM
            -> FullCom Network Requested

保持通信：

只要仍有任一条件成立，ComM 通常继续保持 FullCom：
    App/User 请求 FullCom
    DCM ActiveDiagnostic
    PNC 仍请求
    BswM/系统策略保持通信

释放通信：

所有 User 释放
DCM InactiveDiagnostic
PNC 无请求
系统允许释放
    -> ComM 进入 Ready Sleep 相关处理
        -> Nm_NetworkRelease
            -> CanNm ReadySleep / PrepareBusSleep / BusSleep
        -> CanSM_RequestComMode(NO_COMM)
9.14 ComM 请求聚合规则

ComM 不是只看一个用户，而是聚合多个来源：

App User
DCM ActiveDiagnostic
BswM / EcuM 通信允许
PNC 请求
模式限制 / 唤醒抑制
Channel/User mapping

基本规则：

任一有效用户请求 FullCom:  通道可能被保持 FullCom。
所有用户都释放:  通道才有机会释放。
存在NoCom/NoWakeup/ComM_CommunicationAllowed/CommunicationAllowed gate(API)=false/LimitToNoCom: FullCom 请求可能被压住。

重要查询接口：

ComM_GetRequestedComMode(User, &mode)  看用户当前请求了什么。
ComM_GetCurrentComMode(User, &mode)  看用户当前实际处于什么通信模式。
ComM_GetMaxComMode(User, &mode)  看该用户当前最大允许通信模式。 如果最大只到 NoCom/SilentCom，FullCom 请求上不去。
9.15 ComM_CommunicationAllowed / CommunicationAllowed gate(API)
ComM_CommunicationAllowed / CommunicationAllowed gate(API)(Channel, TRUE/FALSE)

含义：

这是 ComM 是否允许某通道通信的运行时门控。 常由 BswM / EcuM / 系统模式管理逻辑调用。

影响：

ComM_CommunicationAllowed / CommunicationAllowed gate(API) = FALSE:
    即使 User 请求 FullCom，ComM 也可能不真正拉起 CanSM/Nm。
ComM_CommunicationAllowed / CommunicationAllowed gate(API) = TRUE:
    通道具备被 ComM 拉起的前提之一。

排查：

FullCom 请求失败时，必须查这个状态。 很多项目初始化阶段或睡眠准备阶段，会先禁止通信，等条件满足后再允许。
9.16 ComM 阻塞项全表
NoCom / ComMNoCom(EB) = true
影响: 通道静态/配置层面被限制在 NoCom。
表现: 用户请求 FullCom，但最大允许模式可能不是 FullCom。
检查: ComM Channel 配置。 ComM_GetMaxComMode。
NoWakeup / ComMNoWakeup(EB) = true
影响: 禁止该通道被通信请求唤醒。
表现: 睡眠或低功耗状态下，请求不把通道拉起来。
检查: ComM Channel 配置。 ComM_GetInhibitionStatus。
COMM_MODE_LIMITATION_ENABLED / ComMModeLimitationEnabled(EB) = true
影响: 允许运行时限制 Channel 或 ECU 到 NoCom。
接口: ComM_LimitChannelToNoComMode(Channel, TRUE/FALSE)
      ComM_LimitECUToNoComMode(TRUE/FALSE)
表现: 某个策略把通道压到 NoCom，FullCom 请求上不去。
COMM_WAKEUP_INHIBITION_ENABLED / ComMWakeupInhibitionEnabled(EB) = true
影响: 允许运行时阻止通道唤醒。
接口: ComM_PreventWakeUp(Channel, TRUE/FALSE)
表现: 通道不响应唤醒请求，或者请求后不进入 FullCom。
ComM_CommunicationAllowed / CommunicationAllowed gate(API) = FALSE
影响: 通道运行时不允许通信。
接口: ComM_CommunicationAllowed / CommunicationAllowed gate(API)(Channel, TRUE/FALSE)
表现: 用户请求存在，但 ComM 不往 CanSM/Nm 推进。
User Mapping 错误
影响: User 请求发给了错误 Channel。
表现: ComM_RequestComMode 返回正常，但目标 CAN 通道没变化。
检查: ComM User -> Channel mapping。 DCM/App/BswM 使用的 User Handle。
DCM 未 ActiveDiagnostic
影响: 诊断不会保持 FullCom。
表现: 诊断过程中或诊断后通道被释放。
检查: COMM_DCM_ENABLED / ComMDcmUsage(EB)。
      ComM_DCM_ActiveDiagnostic / InactiveDiagnostic 调用。
      DCM S3 超时和会话状态。
PNC 请求不存在或映射错误
影响: 打开 PNC 后，ComM 可能只按 PNC 请求保持相关网络。
表现: 某些 PN bit 不能保持网络，或者无关 PN 误保持网络。
检查: ComMPnc / PNC ID。
      PNC 与 Channel/User 映射。
      EIRA / ERA ComSignal。
      CanNm PN mask / offset / length。
9.20 ComM 常见故障定位

请求 FullCom 但 Controller 不起来：

1. ComM_RequestComMode 是否调用。
2. User Handle 是否正确。
3. User 是否映射到 ESC_M。
4. ComM_CommunicationAllowed / CommunicationAllowed gate(API) 是否 TRUE。
5. NoCom / NoWakeup / Limitation / Inhibition 是否压住。
6. ComMChId / CanSMComMNetworkHandleRef(EB) 是否绑定 ESC_M。
7. CanSM 是否切 Controller STARTED 失败。

FullCom 起来了但不发 NM：

1. COMM_NM_VARIANT_OF_CHANNEL / ComMNmVariant(EB) 是否 FULL。
2. COMM_NM_ACCESS_NEEDED 是否打开。
3. ComMChannelRef / NmComMChannelRef(EB) 是否 ESC_M。
4. StandardBusType / NmStandardBusType(EB) 是否 CANNM。
5. CanNm channel 是否绑定同一通道。
6. CanNmTxPduRef / CanIf Tx PDU / HTH 是否正确。

诊断能收不能发：

1. 是否处于 SilentCom。
2. CanSM Controller 是否只允许接收。
3. CanTp FlowControl / Response 是否发不出去。
4. ComM 当前模式是否 FullCom。

诊断后不睡：

1. DCM 是否仍 ActiveDiagnostic。
2. S3 是否未超时。
3. App User 是否仍请求 FullCom。
4. BswM 是否保持通信。
5. PNC 是否仍有请求。
6. COMM_T_MIN_FULL_COM_MODE_DURATION / ComMTMinFullComModeDuration(EB) 是否还没到。

通道莫名被唤醒：

1. 是否有 User 请求 FullCom。
2. 是否 DCM Active。
3. 是否 SynchronousWakeUp 带起。
4. 是否 PNC/EIRA/ERA 请求。
5. 是否物理 CAN wake source 导致 ECU 先醒。
