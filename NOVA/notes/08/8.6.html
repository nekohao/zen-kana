4. DF_XY 当前关键快照

4.1 DF_XY 快照逐项解释

ComM Channel = ESC_M, ID 0
    意味着 ComM 里有一个通道叫 ESC_M，通道 ID 是 0。 App / DCM / PNC / BswM 如果要请求这一路 CAN 通信，最终都要落到这个 ComM Channel。
    当前结论：后面 Nm、CanNm、CanSM 都必须引用同一个 ESC_M，否则通路断。
Nm Channel = ChassisCan1NmCluster, ID 0
    意味着 Nm 抽象层有一个 NM 通道，通道 ID 是 0。 Nm 不直接发 CAN，它负责把 ComM 的 NM 请求转给具体 BusNm。
    当前结论：这个 Nm Channel 必须通过 ComMChannelRef / NmComMChannelRef(EB) 对到 ComM 的 ESC_M。
StandardBusType / NmStandardBusType(EB) = NM_BUSNM_CANNM
    意味着 Nm 这个通道下面接的是 CanNm， ComM 调 Nm_NetworkRequest 后，会走到 CanNm_NetworkRequest。
    当前结论：这是 CAN NM 通路，后续排查要看 CanNm / CanIf / CanSM。
CanNm_ChanConfig / CanNmChannelConfig_0(EB)
    意味着 CanNm 当前只有一个主要 Channel 配置实例。
    这个实例里放 NM 周期、Timeout、NID/CBV、UserData、PNC、CarWakeUp 等配置。
    当前结论：改 NM 报文和 NM 状态机参数，主要看这个 Channel。
nmChannelId / CanNmComMNetworkHandleRef(EB) = ESC_M
    意味着 CanNm Channel 绑定到 ComM 的 ESC_M。 ComM 请求 ESC_M 后，Nm/CanNm 才知道操作哪一路 NM。
    当前结论：这条引用是通的；如果发不出 NM，不能优先怀疑这里断。
CanSM Network = ESC_M
    意味着 CanSM 也有一个名为 ESC_M 的 CAN Network。
    ComM 请求 FullCom / SilentCom / NoCom 后，CanSM 用这个 Network 去控制底层 Controller。
    当前结论：CanSM 侧也和 ComM 通道名对齐。
CtrlRef / CanSMController(EB) = ESC_M / ESC_S
    意味着 CanSM 的 ESC_M Network 会一起控制两个 CAN Controller。
    ComM 只有一路 ESC_M 请求时，CanSM 可以把 ESC_M 和 ESC_S 两个 controller 一起 START/STOP/SLEEP。
    当前结论：这不是“两路 NM”，而是一条逻辑 Network 控两个 Controller。
CanIf Controllers: ESC_M = 0, ESC_S = 1
    意味着 CanIf 底层有两个 Controller ID。
    CanIf 的 Rx/Tx PDU 会具体绑定到某个 Controller/HRH/HTH。
    当前结论：NM 报文真正走哪个物理 Controller，要看 CanIf PDU，不只看 CanSM controller list。

核心时间快照：

MainFunctionPeriod / CanNmMainFunctionPeriod(EB) = 5 ms
    意味着 CanNm 主函数 5ms 调一次。
MsgCycleTime / CanNmMsgCycleTime(EB) = 100 ms
    意味着正常 NM 周期发送间隔是 100ms。 CanNm 处于需要周期发 NM 且底层可发时生效。
    当前结论：客户说“NM 周期”，主要看这个参数；但底层未 FullCom/未 STARTED 时它不会让 NM 发出来。
CanNmMsgCycleOffset / CanNmMsgCycleOffset(EB) = 5 ms
    意味着本节点 NM 首发相位偏移 5ms。 用来避免多个节点同一时刻一起发 NM。
    当前结论：它影响首发错峰，不是正常周期本身。
MsgTimeoutTime / CanNmMsgTimeoutTime(EB) = 40 ms
    意味着本节点发出 NM 后，等待 TxConfirmation 的超时时间是 40ms。 目的是“我这帧 NM 有没有发送确认”。
    当前结论：它不是网络管理 Timeout；发不出/TxConfirm 不回时看它。
CanNmTime / CanNmTimeoutTime(EB) = 1 s

意味着 CanNm 的 NM Timeout Timer 时间是 1s。它不能简单理解为“1s 没收到 NM 报文就进入 ReadySleep”。
需要区分当前 CanNm 所在状态：
1. 如果当前在 Normal Operation：
   CanNmTimeoutTime 到期后，通常是重启 NM Timeout Timer，并可能报 CANNM_E_NETWORK_TIMEOUT。
   它不会因为 Timeout 到期就直接进入 ReadySleep。
   从 Normal Operation 进入 ReadySleep 的关键条件是本地 Network Release，也就是本节点已经释放网络请求。
2. 如果当前已经在 ReadySleep：
   此时如果 1s 内没有有效 NM 活动继续刷新 / 保持 NM Timeout Timer， CanNm 才会从 ReadySleep 进入 PrepareBusSleep。
当前结论：客户问“对端不发后多久认为网络释放”，不能只看 CanNmTimeoutTime。
这个配置项更准确表示为：本节点已释放网络并处于 ReadySleep 后，如果 1s 内没有有效 NM 活动，则进入 PrepareBusSleep。
   它不等于最终睡眠时间，最终进入 BusSleep 还要继续叠加 CanNmWaitBusSleepTime，并受 ComM / CanSM / 本地 Network Request / 其它节点 NM 活动影响。
RMSTime / CanNmRepeatMessageTime(EB) = 515 ms
    意味着 RMS 持续 515ms。 这是状态持续窗口，不是快发慢发周期。
    当前结论：客户问“Repeat Message 持续多久”，看它；客户问“NM 周期”，看 MsgCycleTime / CanNmMsgCycleTime(EB)。
WBSTime / CanNmWaitBusSleepTime(EB) = 5 s
    意味着在 PrepareBusSleep 后等待 5s 才进入 BusSleep。 它是 NM 睡眠前等待，不是 EcuM 最终下电。
COMM_T_MIN_FULL_COM_MODE_DURATION / ComMTMinFullComModeDuration(EB) = 5 s
    意味着 ComM 进入 FullCom 后至少保持 5s。 即使上层释放请求，也可能要等最短 FullCom 时间到。
    当前结论：诊断/应用释放后不立刻睡，先查这个是否还没到。
ModeReqRepTime / CanSMModeRequestRepetitionTime(EB) = 5 ms
    意味着 CanSM 请求 CanIf/CanDrv 切 Controller 模式失败时，每 5ms 重试一次。
    它影响 Controller START/STOP/SLEEP 模式切换重试节奏。
    当前结论：ComM 请求 FullCom 但 Controller 起不来时，要看 CanSM 重试和 mode indication。
BorTimeL1 / CanSMBorTimeL1(EB) = 0.5 s
    意味着 BusOff 后 L1 快速恢复等待 0.5s。 偶发 BusOff 时恢复比较快。
    当前结论：BusOff 快恢复阶段看它。
BorTimeL2 / CanSMBorTimeL2(EB) = 2.0 s
    意味着连续 BusOff 进入 L2 后，恢复等待 2s。 L2 比 L1 更保守。
    当前结论：频繁 BusOff 后恢复变慢，是这个阶段在起作用。
BorTimeTxEnsured / CanSMBorTimeTxEnsured(EB) = 1.0 s
    意味着 BusOff 恢复后还要观察 1s 稳定发送。 稳定后 CanSM 才认为恢复可靠。
    当前结论：BusOff 恢复不是 Controller 一 STARTED 就算彻底结束。

功能开关快照：

COMM_PNC_SUPPORT / ComMPncSupport(EB) = false
    意味着 ComM 全局不支持 PNC。 ComM 不会按 PNC 对象管理功能簇请求。
CANNM_PN_SUPPORTED / CanNmPnSupported(EB) = false
    意味着 CanNm 全局不支持 PNC。 CanNm 不会按 PN vector / PN filter mask 解析 NM 里的 PN 信息。
    当前结论：即使 CANNM_PN_INFO_OFFSET / CanNmPnInfoOffset(EB) 有值，当前也不生效。
CANIF_PUBLIC_PN_SUPPORT / CanIfPublicPnSupport(EB) = false
    意味着 CanIf 不启用 Partial Network features。
    CanIf PN filter 和部分 transceiver PN 通知链不会按 PN 生效。
    当前结论：底层 PN 支持当前关闭。
CANSM_PNSUPPORT / CanSMPNSupport(EB) = false
    意味着 CanSM 不启用 Partial Networking 支持。
    CANSM_PARTIALNETWORKING / CanSMActivatePN(EB) 即使有字段，也不能形成有效 PN 模式管理。
    当前结论：CanSM 当前不参与 PN 唤醒链。
CanNmCarWakeUpRxEnabled / CanNmCarWakeUpRxEnabled(EB) = false
    意味着 CanNm 不解析收到 NM PDU 里的 CarWakeUp bit。 byte/bit 配置值不会触发 CarWakeUp 语义。
NM_CAR_WAKEUPRX_INDICATION / NmCarWakeUpRxEnabled(EB) = false
    意味着 Nm 抽象层也不启用 CarWakeUp 接收语义。 即使 CanNm 侧打开，Nm/BswM/EcuM 上报链也要同步确认。
    当前结论：当前 CarWakeUp 链路整体不成立。
CANNM_USER_DATA_ENABLED / CanNmUserDataEnabled(EB) = true
    意味着 CanNm 支持 UserData API 方式访问 NM UserData。
    可以通过 Nm_SetUserData / CanNm_SetUserData 类接口处理用户数据，具体看配置和实现。。
CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB) = false
    意味着 NM UserData 不是由 COM 信号来填。 不能按“ComSignal 自动填 NM UserData”理解当前工程。
    当前结论：当前 UserData 是 API/内部方式，不是 COM 信号来填。
UserDataLength / CanNmUserDataLength(EB) = 6
    意味着 8 字节 NM PDU 扣掉 NID 和 CBV 后，剩余 6 字节 UserData。 当前布局就是 Byte2~Byte7。
    当前结论：PNC/CarWakeUp/UserData 如果启用，通常都要在这 6 字节里分配含义。
CANNM_NODE_ID_ENABLED / CanNmNodeIdEnabled(EB) = true
    意味着 NM PDU 会携带 Node ID。 对端可以从 NM 报文识别发送节点。
    当前结论：当前 Byte0 的 NID 有效。
CanNmNodeId / CanNmNodeId(EB) = 8
    意味着本节点发送 NM 时，NID 字节填 8。
NidPos / CanNmPduNidPosition(EB) = CANNM_PDU_BYTE_0
    当前结论：NM 报文 Byte0 = NodeId。
CbvPos / CanNmPduCbvPosition(EB) = CANNM_PDU_BYTE_1
    意味着 CBV 放在 Byte1。CBV 承载 Repeat Message Request、Active Wakeup、PNI 等控制位。
COMM_NM_VARIANT_OF_CHANNEL / ComMNmVariant(EB) = FULL
    意味着ComM 会通过 Nm_NetworkRequest / Nm_NetworkRelease 参与 NM 网络管理。
    当前结论：ComM 不只是控制 CanSM，还会联动 Nm/CanNm。
CANSM_ENHANCED_BUSOFF_REPORTING / CanSMEnhancedBusOffReporting(EB) = true
    意味着 CanSM 启用增强 BusOff 上报能力。 BusOff 恢复状态和 DEM 上报会更完整。
    当前结论：BusOff 排查要看 CanSM BOR 和 DEM 事件，不要只看 CanNm。

12. 客户需求怎么落配置

客户需求/问题先确认主改/主查配置联动风险验证点
NM 周期改为 X ms是正常周期，还是唤醒初期快发？MsgCycleTime / CanNmMsgCycleTime(EB)周期变小会增加 BusLoad；周期变大可能影响对端 Timeout。Trace 看 NM 周期
唤醒后快速发 N 帧，间隔 X msN 是否大于 1；是否真的需要 immediate NM。ImmediateNmTransmissions / CanNmImmediateNmTransmissions(EB)、ImmediateNmCycleTime / CanNmImmediateNmCycleTime(EB)短时间负载增加；RepeatMessageTime必须大于快发序列时间。Trace 看唤醒初期是否出现 N 帧快发
Repeat Message 持续 X ms客户说的是 Repeat 状态窗口，不是 NM 周期。RMSTime / CanNmRepeatMessageTime(EB)影响唤醒扩散、节点发现、Repeat Message Request 行为。状态机日志/Trace 看 RMS 持续时间。

NM UserData 长度/内容UserData 是 API/internal，还是 COM 信号承载？CANNM_USER_DATA_ENABLED / CanNmUserDataEnabled(EB)、UserDataLength / CanNmUserDataLength(EB)、CANNM_COM_USER_DATA_SUPPORT / CanNmComUserDataSupport(EB)PN Info、CarWakeUp、UserData 可能争用字节布局。Trace 看 Byte2~Byte7；生成代码/接口确认数据来源。

Car WakeUp bit 在 byte/bit这是 NM 报文语义，还是硬件唤醒源？CanNmCarWakeUpRxEnabled / CanNmCarWakeUpRxEnabled(EB)、NM_CAR_WAKEUPRX_INDICATION / NmCarWakeUpRxEnabled(EB)、

Dcm_RxComMChannelIDs / DcmDslProtocolRxComMChannelRef(EB)		还会受 NoCom/NoWakeup/CommunicationAllowed 限制。诊断开始看 ComM_DCM_ActiveDiagnostic；结束看 InactiveDiagnostic。

13. 排查清单：故障现象到定位路径

定位原则排查要从“现象”倒推链路，不要从“字段名”倒推。每个问题都要同时看状态机、PDU 映射、生成代码和总线 Trace。

13.1 改配置前先确认

确认项为什么重要
客户需求到底是周期、状态持续时间、Timeout，还是物理唤醒？同一句“多久睡/多久发”可能分别对应 CanNm、ComM、CanSM、EcuM。
当前通道是哪个 ComM Channel / CanSM Network / CanNm Channel？防止改错网络或改了一个没有被引用的 Channel。
NM 报文物理走哪个 Controller？CanSM 管两个 Controller 不等于一帧 NM 自动发到两个 Controller。
当前功能是否真的开启？PNC、CarWakeUp、BusLoadReduction、Immediate NM 等都有总开关/通道开关。
客户 Matrix 和 EB 配置是否一致？NID/CBV/PN/UserData 字节位置必须和对端一致。

13.3 故障现象到排查路径

现象第一层第二层第三层最后确认
不发 NMComM 是否 FullCom，是否被 NoCom/NoWakeup/CommunicationAllowed 压住。CanSM Controller 是否 STARTED，CanIf PDU mode 是否允许 Tx。CanNm 是否 NetworkRequested / Repeat / Normal，TxPduRef 是否正确。CanIf TxConfirmation、总线 Trace、HTH/CAN ID/DLC。
收不到 NMTrace 先确认总线上是否有对端 NM。CanIf Rx ID/Range/HRH/DLC 是否匹配。CanNmRxPduRef 是否引用正确 CanIf Rx PDU。CanNm_RxIndication 是否进来，CBV/NID/PN 解析是否正确。
释放后不睡ComM User/DCM/BswM/App/PNC 是否还保持 FullCom。ComMTMinFullComModeDuration 是否未到。CanNmTimeoutTime、ReadySleep、PrepareBusSleep、WaitBusSleepTime 是否按预期走。EcuM/CanTrcv/硬件下电链路是否还有保持源。
FullCom 不起来User Mapping、ComM_RequestComMode 是否正确。CommunicationAllowed、Mode Limitation、Wakeup Inhibition 是否挡住。CanSMComMNetworkHandleRef、Controller mode indication 是否正确。Nm/CanNm 引用是否对齐，CanIf PDU 是否通。
PNC 不工作确认 ComM/CanNm/CanIf/CanSM PNC 总开关都打开。PNC mapping、PN info offset/length、PN filter mask 是否一致。Com EIRA/ERA、PduR routes、BswM rules 是否完整。Trace 看 PNI + PN vector；验证目标 PNC 是否保持/释放。
时间不准确认主函数周期是否就是配置里的 MainFunctionPeriod。确认配置值是否能被 MainFunctionPeriod 整除。生成代码 tick 是否按预期换算。Trace/日志测量是否从正确状态边界开始。
BusOff 反复先确认是 L1 还是 L2 阶段。看 CanSM BOR 参数和 DEM 上报。查 CanIf/CanDrv mode、TxEnsured 观察期。查物理层、ACK、波特率、采样点、终端电阻、ID 冲突、BusLoad。

14. 开关联动速查：不用全背但要知道谁影响谁

记忆方式不用机械背所有开关，但要知道哪些开关会改变状态机、报文布局、收发路径和跨模块联动。
类型必须关注的开关/参数影响范围现场判断
ComM 模式控制ComMNmVariant、ComMDcmUsage、ComMTMinFullComModeDuration决定是否通过 Nm 管网络、诊断是否能保持通信、FullCom 最短保持时间。诊断后不睡、FullCom 不起来，先看这些。
ComM 限制/抑制ComMNoCom、ComMNoWakeup、ComMModeLimitationEnabled、ComMWakeupInhibitionEnabled可能压住 FullCom 或阻止唤醒。请求存在但通道不起，查 MaxMode 和 inhibition status。
CanNm 时间MsgCycleTime、MsgTimeoutTime、TimeoutTime、RepeatMessageTime、WaitBusSleepTime决定 NM 周期、TxConfirm 超时、网络超时、Repeat 状态、PrepareBusSleep 等待。客户说“时间不对”，先分清是哪种时间。
CanNm 报文布局NidPosition、CbvPosition、UserDataLength、NodeId影响对端解析和本节点 NM 内容。内容不对时查 Matrix、CanNm、CanIf 三者一致性。
PNCComMPncSupport、CanNmPnSupported、CanIfPublicPnSupport、CanSMPNSupport必须端到端打开才形成 PNC 链路。当前 DF_XY 全关，不能用 PNC 解释当前网络保持。
CarWakeUpCanNmCarWakeUpRxEnabled、NmCarWakeUpRxEnabled决定是否解析 NM PDU 里的 CarWakeUp bit 并上报。当前关闭，byte/bit 配置不会形成 CarWakeUp 语义。
CanSM BusOffBorTimeL1、BorTimeL2、BorCounterL1ToL2、BorTimeTxEnsured、DEM event决定 BusOff 恢复节奏和诊断上报。BusOff 问题不要只看 CanNm。
CanIf 收发路径Rx/Tx PDU、CAN ID、HRH/HTH、Range、DLC、UpperLayer决定 NM 报文能不能进/出 CanNm。Controller 已 STARTED 但报文不通，重点查 CanIf。

15. 常见排查入口：一页现场卡

入口一眼判断链路最容易误判的点
不发 NMComM FullCom -> CanSM STARTED -> Nm/CanNm NetworkRequest -> CanIf TxPdu/HTH -> TxConfirmation/Trace只改 CanNmMsgCycleTime 不能让没起来的 Controller 发 NM。
收不到 NMTrace 有帧 -> CanIf Rx ID/Range/HRH/DLC -> CanNmRxPduRef -> CanNm_RxIndicationCanIf 收不到时，CanNm 配再对也没用。
诊断不通ComM FullCom -> CanSM STARTED -> CanIf PDU mode -> CanTp/PduR/DCM 路由 -> 会话/安全/S3诊断报文内容归 DCM/CanTp；通道能不能通信归 ComM/CanSM。
诊断后不睡DCM Inactive -> ComM 请求源清空 -> TMinFullCom 到期 -> CanNm Timeout -> WaitBusSleep -> EcuM/CanTrcv不能把“5s 不睡”直接等同于 CanNmWaitBusSleepTime。
BusOffCanSM BOR -> L1/L2/TxEnsured -> DEM -> CanIf/CanDrv -> 物理层/ACK/BusLoadBusOff 不是 NM 协议问题。
PNCComM PNC -> CanNm PN Info/PNI -> CanIf/CanSM PN -> Com EIRA/ERA -> PduR/BswM/EcuM只打开 CanNm 的 PN 不等于 PNC 生效。
唤醒物理唤醒源 -> EcuM/CanTrcv/CanIf -> ComM 逻辑请求 -> CanSM STARTED -> Nm/CanNm 网络保持CarWakeUp、ActiveWakeup、SelectiveWake、PNC 不是同一个概念。
