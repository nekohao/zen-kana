# 减脂钻石奖励系统

本次只增加减脂奖励模块。积分、转盘、原积分商城保持原有逻辑。管理员和游客沿用现有身份体系。

## 管理员界面

减脂首页显示「记录体重」「钻石商城」、钻石余额、背包剩余次数。有宝宝已完成但尚未确认的服务时，显示「宝宝已经进行服务，是否确认？」入口。

钻石商城只有一个商品：「口」一次，价格 1 颗钻石。兑换后扣钻石、增加一次背包；兑换本身不会直接向游客发起请求。背包点击「使用」并确认后，背包减少一次，产生独立的服务请求。

商城沿用现有积分商城的贴底玻璃面板、居中标题和分段导航，分为「商品」「我的背包」「服务详情」。没有额外的关闭按钮；从顶部横条或标题区域下拉即可关闭，轻拉松手会回弹。内容区域仍可正常滚动，横条也支持键盘 Enter/空格关闭。

面板使用静态浅色渐变保留玻璃风格，避免背景、面板和顶部栏叠加实时模糊；拖动按显示帧合并更新。商城没有手动刷新按钮，打开商城、回到页面和操作成功时自动同步，相同数据不重复重建内容。

商城还显示本周暂估奖扣、记录天数与比较基准、下次结算时间、最近 8 周结算记录。首周显示「对比起始体重」，之后显示本周与上周记录天数。暂估值不等于已到账的钻石，结算时仍可能变化。

## 游客界面与完整流程

游客减脂首页保留「总览」，增加「服务详情」，无需登录。

1. 管理员花费 1 颗钻石兑换「口」一次，奖励进入背包。
2. 管理员使用背包奖励，游客服务详情显示「哥哥请求兑换口一次」。
3. 游客进行服务后点击「已进行服务」并确认，状态变为等待哥哥确认。
4. 管理员打开首页待确认提示，选择「是，确认完成」并确认，本次兑换结束。
5. 若选择「否，退回背包」并确认，背包恢复一次；钻石不会退还，也不会再扣一次。
6. 退回的奖励以后可以再次使用，新建请求；旧请求保留「已退回背包」状态。

请求保留发起、已服务、处理时间。每次加载最近 30 条，可点击「查看更早请求」继续查看。游客只可以把待服务请求标记为已服务；完成或退回由管理员决定。

## 钻石奖扣

时间统一为北京时间（Asia/Shanghai），固定周一至周日。**每周日 12:00 结算**。首次记录所在周，用本周平均体重与管理员设置的起始体重比较；第二周起，比较本周与上周的记录均重。

首周至少记录 **3 个不同日期**，并设置起始体重，就可以奖扣，无需等第二周。首周不足 3 天或未设置起始体重，不奖不扣。后续仍要求两周各至少记录 **3 个不同日期**，否则不奖不扣；漏记或中断后恢复记录，不会再次触发首周例外。按实际记录天数求平均，不对漏记日期补值。同一天如有历史重复记录，取最早一笔（相同时间再按记录 ID 排序）。

首周以「本周均重 − 起始体重」为差值，之后以「本周均重 − 上周均重」为差值。计算使用数据库的原始精度，不先对展示数值四舍五入。

| 平均体重变化 | 钻石变化 |
| --- | --- |
| 减少 0.3 斤 | 0 |
| 减少 1 斤 / 1.2 斤 | +1 |
| 减少 2.3 斤 | +2 |
| 持平 | 0 |
| 增加 0.3 斤 / 1 斤 / 1.8 斤 | −1 |
| 增加 2.3 斤 | −2 |

余额最低为 0。余额不足时只扣剩余余额，结算记录同时保存原应奖扣数和实际奖扣数。

**周日中午截止的具体含义：**这一周只统计周一 00:00 至周日 12:00 之前提交的记录；12:00 及之后的记录仍保留在原体重记录和总览中，但不参与这一周钻石结算，也不会移到下一周。每周平均值均按这个相同截止时间计算。

结算后保存均重、天数与比较基准快照。首周使用结算时设置的起始体重，并冻结该基准。之后补录、删除记录、修改起始体重，不会改写已结算奖扣；下周比较时沿用上一周已冻结的均值。本模块使用实际体重求均值。绝对均重和起始基准只存在数据库内部，接口不会返回实际体重。

升级首周规则时，需要再次执行 `fat-rewards.sql` 整个文件。脚本保留已有余额、背包、服务与结算历史；已结算的周不会重新奖扣，新的首周规则适用于尚未结算的周。

初始钻石与背包均为 0。首次部署从尚未截止的当前周开始；若已经过本周日 12:00，则从下周开始。启用前已结束的周不补发或补扣。再次执行迁移不会重置余额、背包、请求或结算进度。

## 更新与开销

数据库每周运行一次结算任务，页面关闭仍可结算。进入减脂、打开商城/服务详情、手动刷新、回到应用时同步状态，操作成功后直接使用接口返回的新状态。没有新增前端定时轮询或常驻连接。并发刷新会合并，回到应用的重复事件会合并。

服务状态不是实时推送；重新进入、回到应用或点击刷新即可同步。每周任务如果漏跑，下一次同步会补结算已经到期的周，每周只结算一次。

新增前端文件约 21 KB（JS + CSS，未压缩），没有新增前端框架或生产运行依赖。使用原有玻璃面板、绿色按钮与弹层布局。购买/使用有操作 ID，网络响应丢失后，包括刷新页面后，重试不会重复扣钻石或重复发起服务。

## 上线步骤

本地代码完成不代表 Supabase 或 GitHub Pages 已更新。部署顺序如下：

1. 在 Supabase 项目的 SQL Editor，以 `postgres` 执行 **fat-rewards.sql 整个文件**。脚本会新增 4 张私有表、受控接口和每周任务；不会修改原有模块的表或函数。
2. 如果提示 `pg_cron` 无法启用，先在 Supabase 的 Integrations → Cron 中启用模块，再重新执行。参考 [Supabase Cron 安装文档](https://supabase.com/docs/guides/cron/install)。
3. 检查脚本最后返回的任务：`points-fat-rewards-sunday-noon`，`active=true`。GMT/UTC 的表达式是 `0 4 * * 0`；Cron 为 Asia/Shanghai 时是 `0 12 * * 0`。其他 Cron 时区会明确报错，整次迁移回滚，避免错误时间结算。
4. 将 `index.html`、`fat-loss.js`、`fat-rewards.js`、`fat-rewards.css` 更新到 GitHub Pages 对应的 `points` 目录。保留已有 `fat-loss.css` 等资源。SQL 与测试文件无需作为页面资源上传。
5. 手机刷新页面：管理员登录后打开减脂 → 钻石商城；游客直接打开减脂 → 服务详情。部署后余额为真实的 0，预览图中的钻石是本地模拟数据。

只更新前端而未执行 SQL 时，商城会显示「钻石功能尚未部署」，原有体重功能仍可使用。

## 本地验证

已在 PGlite（PostgreSQL 的本地 WASM 运行环境）中执行实际迁移，使用提供的 CSV 中原有减脂函数和管理员判断函数，通过 108 项数据库检查，包括首周起始体重比较、首周不足天数、缺少起始体重、第二周恢复周均比较、冻结基准与旧结构升级。测试没有连接线上数据库。`pg_cron` 的调度接口在该环境中用本地替身核对任务名和时间；上线后仍需核对真实 Cron 任务运行记录。

PGlite 不支持独立客户端同时执行 SQL，测试中的竞争操作会排队；数据库跨连接竞争的保障来自实际 SQL 的余额行锁、请求行锁和操作唯一键，尚未在真实 Supabase 多连接环境进行压力测试。

浏览器使用本地模拟数据走通兑换、使用、游客标记已服务、管理员确认、退回后重新使用；验证购买响应丢失后刷新页面重试，包括余额为 0 时确认原购买结果，均不会重复扣费。检查了 390 和 320 像素宽的手机布局。

过程中的测试脚本、预览模拟器和截图只保留在本地，不随正式功能提交。生产页面不含模拟余额或测试账号。
