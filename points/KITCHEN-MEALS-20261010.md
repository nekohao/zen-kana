# 按餐次预约与补菜

点击「预约点菜」，先选今天或未来日期，再选早饭、午饭或晚饭，之后挑菜与填写要求。
同一天同一餐会打开原菜单。已做好的菜保留完成状态，新增菜等待制作；宝宝也可以将额外做好的菜补记到同一餐。
全部菜做好后，哥哥逐菜评价并统一结算，一餐只记一次积分变动。评价结算后不再补菜。

## 数据库升级

在 Supabase SQL Editor 以 postgres 执行 `kitchen-meals-increment-20261010.sql` 全文。
前提是已有 `kitchen-increment-20261008.sql` 的厨房结构与接口。不需要执行重新建库或原始初始化脚本。

增量文件可重复执行。保留余额、历史积分、评价和菜单版本；已有明确用餐日期和餐次、且同一餐不存在重复记录的历史餐次会沿用。
无法确定餐次的历史点菜，以及同一日期餐次存在多条历史记录的情况，保留原记录，不猜测、不合并、不重新计分。

新接口使用同一天同一餐唯一约束、版本检查、事务锁和持久操作 ID。
旧客户端不能新建不带日期的点菜，也不能改写已升级餐次；原历史记录仍可完成、拒绝、评价和结算。
制作完成后补菜会使整餐回到待制作，先前做好的菜不回退。已做好的菜不能移除；整餐尚有菜未做好时不能评价结算。
未做菜的预约可以取消；做过菜的餐次不能整餐取消或拒绝。未来预约不会提前标为制作完成。

前端未检测到餐次升级接口时保留只读查看，提示先执行 SQL，并禁用新的预约与补菜操作。
旧厨房读接口仍能用于查看菜谱、历史餐次和已有评价。

测试数据库只在本地内存运行，不访问线上 Supabase。界面联动测试使用模拟 DOM，不代表实际 iPhone 布局验收。
